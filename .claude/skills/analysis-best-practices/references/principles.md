# 分析フレームワークの原則

## 1. 問いファースト（イシュー・ドリブン）

数字を集めてから「何か言えることはないか」と探すのは非効率で、都合の良い結論に流されやすい。
先に「何を明らかにしたいか」を1文で固定してから、それに答えるために必要なデータだけを見る。

- 悪い例: 「アクセス数のデータを分析してください」
- 良い例: 「先週アクセス数が落ちたのは、投稿頻度が原因か、内容が原因か」

問いが大きすぎる場合は、答えられる大きさまで分解してから着手する（下記のMECE分解）。

## 2. MECEな要因分解（ロジックツリー／フィッシュボーン図）

原因や選択肢を「漏れなく、重複なく（Mutually Exclusive, Collectively Exhaustive）」列挙してから、
データで絞り込む。思いついた1つの仮説に飛びつくと、本当の原因を見逃す。

- **ロジックツリー**: 問いを枝分かれさせて分解する（例: 「登録者が減った」→「新規流入が減った」
  「既存視聴者が離脱した」→ さらに分解）。
- **フィッシュボーン図（特性要因図）**: 結果を魚の頭に置き、骨に「人・仕組み・環境・データ」など
  カテゴリ別の原因候補を並べる。トヨタ生産方式で品質管理に使われた手法。
- コツ: 分解した時点では「正しさ」を問わない。まず全部出してから、データで淘汰する。

## 3. なぜなぜ分析（5 Whys / Root Cause Analysis）

表面的な現象（症状）に対策を打っても再発する。「なぜ」を繰り返し、構造的な原因
（設計判断・仕組み・プロセスの欠陥）に到達するまで掘り下げる。目安は5回だが、根に到達したら
早く止めてよいし、複雑な問題なら5回を超えてもよい。

例（トヨタ方式の定番例）:
1. なぜ機械が止まったか → ヒューズが飛んだから
2. なぜヒューズが飛んだか → 軸受の潤滑が不十分だったから
3. なぜ潤滑が不十分だったか → 潤滑ポンプが十分汲み上げていないから
4. なぜ十分汲み上げていないか → ポンプの軸が摩耗していたから
5. なぜ摩耗していたか → ストレーナー（濾過器）がついておらず、切粉が入り込んだから
→ 対策は「ヒューズ交換」ではなく「ストレーナーの取り付け」になる。

Amazonの「Correction of Errors（COE）」もこの考え方を採用しており、事後対応（symptom対処）で
終わらせず、根本原因への対策を義務付けている（`case-studies.md` 参照）。

## 4. 相関と因果を区別する

2つの数値が同時に動いたからといって、一方が他方の原因とは限らない。以下を確認するまで因果と
書かない。

- **比較対象（対照群）はあるか** — 施策を打った期間だけでなく、打たなかった場合の見込み・
  他チャンネル/他期間との比較があるか。
- **交絡要因はないか** — 両方の数字を同時に動かす別の要因（季節性、外部トレンド、母数の変化）
  がないか。
- **時間的順序は正しいか** — 原因とされる事象が結果より前に起きているか。
- **母数は十分か** — 少数のサンプルからの結論は偶然の可能性を疑う。

チャレンジャー号の事故（`case-studies.md`）は、「故障が起きなかったデータを除外してグラフを
書いた」ことで温度との相関を見誤った典型例。除外したデータこそが重要な情報を持つことがある。

## 5. バイアスの自己点検

分析者自身の思考の癖が結論を歪めることが多い。以下を都度チェックする。

- **確証バイアス** — 自分の仮説を支持するデータばかり探し、反証を軽視していないか。
- **生存者バイアス** — 成功した事例・残ったデータだけを見て、脱落・失敗したものを見ていないか
  （例: 「当たった予想」だけを振り返り、外れた予想の傾向を見ない）。
- **基準率の無視（Base Rate Neglect）** — 目立つ個別事例に引っ張られ、そもそもの母数・発生確率を
  無視していないか。
- **選択バイアス** — 分析対象のデータ自体が偏った集め方をされていないか。
- **アンカリング** — 最初に見た数字や仮説に引きずられて、他の見方を検討しなくなっていないか。

## 6. 整合性チェック（クロスバリデーション的思考）

同じ結論を別の算出方法でも導けるか突き合わせる。1つの指標・1つの計算式だけを信じない。
本リポジトリの `youtube/js/insight.js` は、平均視聴時間を「APIの値」と「総再生時間÷視聴回数」の
2通りで計算し、食い違いがあれば「別のものを測っている」合図として扱っている。これは良い実践例。

## 7. プレモータム（事前検死）分析

結論や施策を決定する前に、「もしこれが外れる/失敗するとしたら、原因は何か」をあらかじめ
洗い出しておく手法。決定後に後悔してから原因を探る（ポストモータム）よりも、事前に弱点を
補強できる。予測・投資判断・施策実行の前に一度立ち止まって使う。

## 8. 不確実性を明示する

サンプルが小さい・偶然の可能性が残る・因果まで立証できていない場合は、そう明記する。
「〇〇である」と断定せず、「〇〇の可能性が高いが、△△の検証はできていない」のように、
確信度と根拠の強さを対応させる。過度に精密な数字（例: 母数10件で「73.2%」と言う）で
確信度を偽装しない（false precision）。

## 9. ピラミッド原則（結論ファーストの伝え方）

分析結果を伝えるときは、経緯を時系列で説明するのではなく、結論を先に述べ、それを支える根拠を
MECEに並べる（バーバラ・ミント『考える技術・書く技術』）。読み手は「何が言いたいか」を先に
知りたい。

## 10. 可視化との連携

グラフ・チャートで分析結果を見せる場合は `dataviz` スキルの色・軸・注釈の原則も併用する。
分析の質が高くても、誤解を招くグラフ（切り詰めた軸、恣意的な期間の切り取り）は結論を歪めて
伝えてしまう。
