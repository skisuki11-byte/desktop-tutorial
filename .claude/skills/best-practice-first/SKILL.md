# 世の中のベストプラクティスを常に見る癖

ユーザーの恒久的な方針: 資料・プラン・提案・レポート・画面などを作るときは、必ず世の中の
成功事例・失敗事例をよく分析し、それをベストプラクティスとして落とし込んで作る。これは
「言われたときだけやる」ものではなく、資料作成のたびに自動的に踏む標準ステップとして扱う。

## 適用範囲

- ドキュメント・レポート・提案書・企画書・README・仕様書 などのテキスト資料
- プレゼン・スライド
- 画面・アプリのUI/UXデザイン（この場合はさらに `design-best-practices` スキルを併用し、
  そちらの成功/失敗事例・原則・チェックリストを使う）
- その他「まとめて」「作って」「提案して」と頼まれるあらゆる成果物

## 標準ワークフロー（毎回これを踏む）

1. **お題の分野を特定する** — 何についての資料か（例: 家計管理、投資、学習継続、動画運用、
   アプリのUI、etc.）を明確にする。
2. **実在の成功事例・失敗事例を最低1つずつ思い出す/調べる** — 抽象論ではなく、実際の企業・
   製品・サービス・研究など固有名詞のある事例を使う。知識で足りない場合や事実確認が必要な場合は
   WebSearch 等で裏取りする。曖昧な記憶のまま断定しない。
3. **各事例から教訓を1〜2文で抽出する** — 「なぜ成功したか／なぜ失敗したか」を構造的な理由
   （設計判断・意思決定・プロセス）に還元する。
4. **教訓をベストプラクティスとして資料の構成・内容に反映する** — 見出し構成、優先順位、
   何を入れて何を削るかを、事例からの教訓で裏付ける。
5. **根拠を明示する** — 資料や説明の中で「〇〇の事例に基づき」「△△の失敗を踏まえ」のように、
   最低限どの判断がどの事例に基づくかを分かる形にする（すべての箇所に注釈は不要。要所で十分）。
6. **見た目が絡む場合は design-best-practices を併用する** — 画面・レイアウト・配色などが
   関わる資料は、このスキルの手順1〜5に加えて `design-best-practices` スキルの原則・
   チェックリストも適用する。

## やってはいけないこと

- 事例の裏付けなしに「一般的に良いとされる」だけで資料を作ること
- 存在しない事例をでっち上げること（不確かなら明言せず、確認できた範囲に留めるか調べる）
- 毎回ユーザーに「事例を調べてから作りますか？」と聞くこと（これは標準動作であり、聞かずに実行する）
