# デザイン原則詳細

すべて「なぜそうするか」を成功/失敗事例（`case-studies.md`）で裏付けられる、実装可能なレベルまで落とし込んだもの。

## 1. 視覚的階層 (Visual Hierarchy)

- 1画面に「主役」は1つだけにする。CTA（保存・追加・記録するボタンなど）は1画面1個の強調色。
- サイズ・太さ・色・余白の4手段で優先順位をつける。全部太字・全部同じ色にすると階層が消える。
- 数値主体の画面（家計簿の合計金額、配当金の年間受取額）は「最重要な数字」を最大サイズで置き、
  内訳は一段小さくする（Mint / 家計簿アプリの定番パターン）。

```css
--font-size-display: 2rem;   /* 合計金額など最重要 */
--font-size-title:   1.25rem;
--font-size-body:    1rem;
--font-size-caption: 0.8125rem;
```

## 2. タイポグラフィ

- 日本語 UI のフォントスタック例:
  ```css
  font-family: -apple-system, BlinkMacSystemFont, "Hiragino Sans", "Hiragino Kaku Gothic ProN",
    "Yu Gothic", "Noto Sans JP", system-ui, sans-serif;
  ```
- 本文の行間は 1.6〜1.8（日本語は欧文より行間を広めに取らないと詰まって見える）。
- 金額・日付など桁が揃うべき数字には `font-variant-numeric: tabular-nums;` を指定し、桁がガタつかないようにする。
- 見出しと本文でフォントサイズ比を最低 1.25 倍（できれば 1.5 倍）以上つけて、階層をはっきりさせる。

## 3. 配色とコントラスト

- アクセントカラーは基本1色（+エラー/成功用に各1色）に絞る。色を増やすほど「主役」が分からなくなる（Stripeの教訓）。
- 文字色と背景色のコントラスト比は本文で 4.5:1 以上、大きな見出しで 3:1 以上（WCAG AA）を満たす。
- ダークモードはトーンを反転するだけでなく、影の代わりに「明度差のある面（サーフェス）」で階層を作る
  （Material Design のダークテーマ指針）。
- 色だけで意味を持たせない。家計簿の支出/収入、配当金の増減などは、色（赤/緑）に加えて `+` / `−` や
  アイコンを併用する（色覚多様性対応。信号のような色だけの UI は失敗しやすい）。

```css
:root {
  --color-bg: #f7f7f8;
  --color-surface: #ffffff;
  --color-text: #1a1a1a;
  --color-text-muted: #6b7280;
  --color-accent: #2563eb;
  --color-success: #16a34a;
  --color-danger: #dc2626;
}
@media (prefers-color-scheme: dark) {
  :root {
    --color-bg: #121212;
    --color-surface: #1e1e1e;
    --color-text: #f2f2f2;
    --color-text-muted: #9ca3af;
  }
}
```

## 4. 余白とグリッド

- 4px または 8px を基準単位にしたスペーシングスケールを使う。感覚で `margin: 13px` のような値を使わない。

```css
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-6: 24px;
--space-8: 32px;
--space-12: 48px;
```

- カード・リスト項目など繰り返し要素の内側余白（padding）は必ず同じ値に揃える。バラつきが「雑さ」に見える最大要因。

## 5. 一貫性（デザインシステム的思考）

- 色・角丸（border-radius）・影・アニメーション速度を CSS 変数にして、1つのアプリ内はもちろん、
  cashbook / dividend / yosou / solar / sekaishi / youtube など**アプリをまたいでも極力揃える**。
  同じ作者の複数アプリの見た目がバラバラだと、個々のアプリの完成度が高くても「ブランド」として弱く見える
  （Airbnb DLS・Appleの一貫したHIGが成功した理由の核心）。
- 新しいアプリを作るときは、既存アプリの `css/style.css` や `app.css` にある配色・角丸・余白の値を
  流用できないか先に確認する。

## 6. モーションとフィードバック

- 保存・登録・削除などの操作には 150〜300ms 程度の短いフィードバック（色の変化、チェックマーク、軽いフェード）を入れる。
  無反応な操作は「効いたか分からない」という不安を生む。
- 継続を促したいアプリ（学習・記録系）では、連続記録日数やプログレスリングのような
  ゲーミフィケーション要素が有効（このリポジトリの英単語アプリの「連続学習日数」表示はこの好例。他アプリにも展開できる）。
- `prefers-reduced-motion: reduce` を尊重し、アニメーションを抑える分岐を入れる。

## 7. アクセシビリティ

- タップ対象は最低 44×44px（指での誤タップを防ぐ。すべてスマホ利用前提のアプリ群なので特に重要）。
- キーボード操作時のフォーカスリングを `outline: none` で消さない。消す場合は代替の可視スタイルを必ず用意する。
- フォームや入力には `<label>` を関連付け、装飾用アイコンには `aria-hidden="true"` を付ける。

## 8. 機能を壊さない改悪をしない

- 見た目を刷新するときも、ユーザーが普段使っている操作導線（よく使うボタンの位置、ワンタップで終わる操作）を
  奥に隠したり、手順を増やしたりしない。「良くする」つもりの変更が「前より使いにくい」にならないよう、
  変更前にその画面の「一番使われている操作は何か」を明確にしてから手を入れる。
