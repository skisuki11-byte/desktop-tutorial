# 事例集（セッション最適化）

すべて `session-optimization` スキルの根拠として引用する。抽象論ではなく、固有名詞のある
一次情報・調査結果に基づく。

## 成功事例

### 1. Anthropic「マルチエージェント研究システム」— 役割ごとのモデル使い分け

- 概要: Claude Researchは司令塔（リード）エージェントが計画を立て、3〜5体の並列サブ
  エージェントを立ち上げて調査させ、最後に引用付けの統合を行うオーケストレーター/
  ワーカー構成。リードにOpus、サブエージェントにSonnetを使う設計。
- 結果: 単体Opusエージェントに対して社内評価で90.2%高い成果。トークン使用量そのものが
  成果差の80%を説明する主要因だった（次いでツール呼び出し数、モデル選択）。
- 重要な留意点: この構成は通常のチャットの約15倍のトークンを消費するため、「経済的に
  見合うタスクか」を考えてから使う必要があると明記されている。
- 教訓: 難しい・広い調査には強いモデル＋並列化が効くが、コストも跳ね上がる。だからこそ
  「なんでも並列・なんでも高性能モデル」ではなく、タスクの難度に応じて使い分ける設計が
  重要。
- 出典: https://www.anthropic.com/engineering/multi-agent-research-system

### 2. プロンプトキャッシュによるコスト・レイテンシ削減

- 概要: 同一の長いプロンプト前置き（システムプロンプト、ドキュメント、スキル等）を
  複数リクエストで使い回すキャッシュ機構。Anthropic公式ドキュメントで、長いプロンプトに
  対し最大90%のコスト削減、最大85%のレイテンシ削減が示されている。
- 実例: ProjectDiscovery社は2026年にキャッシュヒット率を7%から84%まで改善し、LLM
  コストを59〜70%削減、98億トークンを本番でキャッシュから提供した。
- 教訓: セッションの先頭（システムプロンプト・CLAUDE.md・スキル等の安定部分）を不用意に
  書き換えず、同じ内容を使い回すほどキャッシュが効き、同じ利用枠でより長く/多く作業できる。
- 出典:
  - https://platform.claude.com/docs/en/build-with-claude/prompt-caching
  - https://introl.com/blog/prompt-caching-infrastructure-llm-cost-latency-reduction-guide-2025
  - https://ngrok.com/blog/prompt-caching

### 5. LLMモデルルーティング/カスケード — 難度に応じた自動振り分け

- 概要: すべてのクエリを安いモデルにまず投げ、自信度が閾値未満の時だけ高性能モデルに
  エスカレーションする「カスケード」方式。事前分類せず結果の確信度で振り分ける。
- 結果: RouteLLMはMT Benchで85%のコスト削減をGPT-4品質の95%を保ったまま達成。
  FrugalGPTは組み合わせを学習することで最大98%のコスト削減を報告。総じて40〜85%の
  コスト削減が品質をほぼ落とさず可能とされる。
- 重要な留意点: 「1日1万リクエスト以上の規模でないと、ルーティングを構築する工数が
  節約分を上回る」と明記されている。
- 教訓: 難度に応じたモデルの使い分けは強力だが、それを自動化する仕組み自体にもコストが
  かかる。個人開発規模では自動化せず、手動のヒューリスティック（作業の種類でモデルを
  選ぶ）で十分に効果が出る。
- 出典:
  - https://tianpan.co/blog/2025-10-19-llm-routing-production
  - https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades
  - https://neuraltrust.ai/blog/llm-model-routing

## 失敗事例

### 3. AutoGPT（2023）— ガードレールのない自律ループ

- 概要: 2023年3月に公開され数週間で15万スター超を獲得した自律型エージェント。だが
  コスト上限も強制終了条件もサンドボックスもなく、GPT-4への呼び出しを推論ステップ毎に
  行う設計だった。
- 結果: 1タスクあたり平均$14.40を消費し、ひどいケースでは同じような検索クエリを繰り返す
  だけの無限ループに陥り、数百ドル分のAPI利用料を浪費した例が報告されている（「検索→
  保存→完全性チェック→やり残しありと判断→似た検索を再実行」を繰り返すパターン）。
- 教訓: 自律的・反復的な処理（ポーリング、自動修正ループなど）には必ず「進捗が出なければ
  止まる」終了条件とチェックポイントを設ける。進捗のないまま同じ操作を繰り返させない。
- 出典:
  - https://github.com/vectara/awesome-agent-failures/blob/main/docs/case-studies/autogpt-planning-failures.md
  - https://dev.to/xu_xu_b2179aa8fc958d531d1/the-autogpt-trap-when-accessible-ai-becomes-your-most-expensive-lesson-3noh

### 4. コンテキスト・ロット（Chroma社, 2025年の検証研究）

- 概要: 18のフロンティアモデルを対象に、入力トークン数を増やしながら性能を計測した研究。
  「情報が入っているかどうか」ではなく「文脈がどれだけ長いか」自体が性能を下げることを
  示した。
- 結果: 関連情報が文脈の中盤にあると精度が3割以上低下する「Lost in the Middle」現象を
  確認。さらに最大コンテキスト長の約50%地点付近で、性能が45.5%も急落する「破局的な
  閾値」が存在するケースも報告されている。
- 教訓: 1つのセッションに無関係な話題・大量の生ログを詰め込んで肥大化させるほど、
  モデルは劣化する。作業単位でセッション/PRを分け、読み込む情報は必要な範囲に絞る
  （`Grep`/`Glob`で当たりを付けてから必要箇所だけ`Read`する、等）ことが、コスト面だけで
  なく回答品質のためにも重要。
- 出典: https://www.trychroma.com/research/context-rot

## 自前検証（このリポジトリでの実測データ）

外部事例の裏付けに加え、このリポジトリ自身で実際にAgentツールを動かして検証した一次
データ。以後の判断はここに書かれた実測値も根拠にしてよい。

### 6. サブエージェント起動コストは内容によらずほぼ固定（3回計測）

- 方法: `Agent`ツールで極小タスク（`ls`相当のファイル列挙）をHaikuの`general-purpose`
  サブエージェントに3回、`Explore`サブエージェントに1回投げて比較した。
- 結果: `general-purpose`+Haikuでの極小タスクは 39,438 / 41,273 / 44,289 トークンと、
  内容（`ls`一発 vs README要約+提案）に関わらずほぼ同水準だった。`Explore`+Haikuでは
  トークン使用量そのものが結果に含まれなかった（ツールの返り値仕様上、内訳が見えない
  ケースがある）。
- 教訓: サブエージェント1回の起動には約4万トークン級の固定費（システムプロンプト・
  ツール定義の読み込み）がかかり、タスクの軽重にほぼ依存しない。単発の小〜中規模作業を
  「モデルが軽いから」という理由だけでサブエージェントに逃がすのは損になりやすい。

### 7. Sonnet vs Opus — 同一プロンプトでの実務調査タスク比較

- 方法: `cashbook/js/store.js`の残高・集計ロジックから実在するバグを1つ特定させる、
  という全く同じプロンプトを、Sonnet（既定）とOpusのそれぞれの`general-purpose`
  サブエージェントに投げて比較した。
- 結果:
  - Sonnet: 72,677トークン、ツール呼び出し1回（対象ファイルのみ読了）、81秒。
    `normalize()`で`date`だけフォールバックが無く、月別集計で`TypeError`が起きうる
    という正当なバグを発見。
  - Opus: 80,235トークン（Sonnet比+約10%）、ツール呼び出し11回（対象ファイルに加え
    `app.js`の呼び出し元まで自発的に追跡）、125秒。CSV取り込み経路だけ収入/支出の
    同時入力バリデーションが抜けており、科目別集計から支出額が警告なく消えて帳票の
    数字が矛盾する、という単一ファイルだけ見ていては気づけない構造的な不整合を発見。
- 教訓: 同一プロンプトでのモデル階層の入れ替え（Sonnet→Opus）によるトークン数の増加は
  10%程度に留まり、Anthropicのマルチエージェント事例が示す「15倍」（並列構成による
  倍率）とは全く別の話だった。Opusは自発的に調査範囲を広げる（ツール呼び出し数が
  11倍）ことで、複数ファイルにまたがる根本原因の調査に真価を発揮する。ただしOpusは
  1トークンあたりの単価もSonnetより高いため、実際の金額差はトークン数の差以上になる
  点には注意する。「原因不明・複数ファイルにまたがる根本調査にはOpus」という方針は、
  このリポジトリでの実測でも裏付けられた。

### 8. 大規模アプリ（7ファイル・4,378行）でのOpus委譲 — 規模が大きいほど固定費の比率は薄まる

- 方法: `youtube/`アプリ（api.js, app.js, chart.js, insight.js, report.js, seo.js,
  store.js、計4,378行）全体の根本的なバグ調査を、メインセッションでは`Glob`/`git log`/
  `wc -l`のみで規模把握（数千トークン）した上でOpusサブエージェント（バックグラウンド）
  に丸ごと委譲した。
- 結果: 168,819トークン、ツール呼び出し12回、243秒。単一ファイル（`cashbook/js/store.js`,
  216行）でのOpus実測（80,235トークン）と比べ、コード量は約20倍なのにトークン消費は
  約2.1倍に留まった。見つかったバグは3件とも、期間切替時のキャッシュ未クリア、OAuth
  トークン再取得時のコールバック競合、複数タブの読み込み順序に依存する診断結果の非決定性
  という、単一ファイルの精読は元より、Sonnet委譲でも構造的に気づきにくい非同期・状態管理系
  の根本原因だった。
- 教訓: サブエージェントの起動固定費（約4万トークン）は、対象が大きいほど全体に占める
  比率が小さくなり相対的に効率が上がる。「大きく独立した調査ほど委譲が割に合う」という
  当初の仮説を裏付ける実測。また、メインセッションで4,378行を直接読んでいたら数万
  トークンをこの会話に恒久的に積み増していたはずで、バックグラウンド委譲によって
  メインの会話コンテキストを汚さずに済んだ（事例4のコンテキスト・ロット対策の実践）。

### 9. Anthropic公式「Effective context engineering for AI agents」（2025年9月）

- 概要: Anthropicが自社のエージェント構築経験から、コンテキストを「有限で貴重な資源」
  として扱うための3つの技法を公式にまとめたもの。
  1. **compaction（圧縮）** — 生のツール出力は処理し終わったら消す「tool result
     clearing」が最も手軽な圧縮で、Claude Developer Platformの機能としても提供されている。
     会話がウィンドウ上限に近づいたら要約して新しいコンテキストで再開する、より強い圧縮も
     ある。
  2. **structured note-taking（構造化されたメモ）** — エージェントがコンテキスト外の
     メモリに定期的にメモを書き、後のターンで読み戻す手法。ポケモンをプレイする
     Claudeエージェントは、数千ステップにわたる目標・探索済み地域・戦闘方針を、
     コンテキストがリセットされてもこの方法で正確に追跡し続けた。
  3. **sub-agent architectures（サブエージェント構成）** — トークンを大量に使う
     サブタスクは専用のサブエージェントに「分岐」させ、きれいなコンテキストで処理させて、
     終わったら要約メッセージだけを本流に「合流」させ、途中の細かいやり取りは畳んでしまう。
- 教訓: このスキルの事例6〜8で実測してきた「Opus/Sonnetサブエージェントへの委譲」は、
  まさに3番目の技法そのものだった（本流の会話には最終結果だけを返し、途中のツール呼び出し
  詳細は畳んでいる）。`ToolSearch`による遅延ツール読み込みや`Grep`/`Glob`優先も1番目の
  「無駄な生データを持ち込まない」という考え方に沿っている。**一方、2番目の
  「構造化されたメモ」＝`TaskCreate`/`TaskUpdate`によるタスク管理は、この会話が長時間・
  複数の作業（cashbook・youtubeの計6件のバグ修正、スキルの検証を何度も繰り返す等）に
  及んでいたにもかかわらず、一度も使っていなかった。**ハーネス自身が繰り返し
  「TaskCreateの利用を検討して」と促していたのに従っていなかった、という実例。
  以後、3ステップ以上・複数の作業にまたがるセッションでは`TaskCreate`/`TaskUpdate`で
  進捗を外部化し、会話の記憶だけに頼らないようにする。
- 出典: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### 10. 自前検証：このセッションでの「必要になるまで読み込まない」の実測

- 方法: このセッション中に実際に流れてきたシステム通知を数えた。接続されたMCPサーバー
  （Canva, github, Gmail, Google_Calendar, Google_Drive, Higgsfield, Notion）が持つ
  ツールの総数は 32+55+29+9+11+91+43 = **270個**。これらは`ToolSearch`により、
  必要になるまでスキーマが読み込まれない「遅延ツール」として扱われていた。
- 結果: このセッションで実際に`ToolSearch`経由でスキーマを読み込んで使ったのは
  `WebSearch`/`WebFetch`と、GitHub関連の十数個程度のみ。残り250個以上のツール定義
  （1つあたり数百トークンになりうるJSON Schema）は一度も会話に読み込まれなかった。
- 教訓: 事例9の「just-in-time retrieval（その場で必要な分だけ取りに行く）」を、
  Claude Code自体の仕組み（`ToolSearch`による遅延ツール定義）としてすでに実践できている
  ことを裏付ける実例。全ツールを毎回読み込む設計だったら、この会話は不要なツール定義だけで
  数万トークン単位を毎ターン消費していたはずで、その分セッションが早く使い切られていた。

### 11. Message Batches API — 別の軸のコスト最適化（このセッションには非該当）

- 概要: Anthropic Messages APIには、即時応答が不要な非同期ワークロード（大量データの
  一括分類・要約・過去ログの再分析など）向けに、入力・出力トークンとも一律50%引きになる
  Message Batches APIがある。プロンプトキャッシュの割引とも併用できる。
- 重要な留意点: これはClaude Code（対話的セッション）には当てはまらない。対話的に
  即座の応答を必要とする作業はそもそもBatch APIの対象外（バッチは最大24時間以内に
  処理される非同期ジョブ）。
- 教訓: 「トークン最適化」といっても軸が違う。Claude Codeのセッション内で効くのは
  事例1〜10のモデル選択・委譲・キャッシュ・コンテキスト管理であり、Batch APIは
  「Claude APIを直接使って大量の非同期処理を自作する」場合にだけ検討すべき、別の
  最適化レバーである。混同しない。
- 出典: https://claude.com/blog/message-batches-api
