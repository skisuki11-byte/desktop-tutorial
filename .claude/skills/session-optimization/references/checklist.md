# 実践チェックリスト（このリポジトリでの使い分け）

## モデル選択の目安

| 作業の種類 | 推奨モデル | 理由 |
|---|---|---|
| 新規アプリ/画面の設計、複数アプリ（cashbook, dividend, yosou, solar, sekaishi, youtube等）にまたがる仕様検討 | Opus（高性能） | 一度の判断ミスが後戻りコストになるため、事例1の教訓通り「難しい・広い」タスクに強いモデルを充てる |
| 原因不明のバグ調査、パフォーマンス劣化の根本原因分析 | Opus | 深い推論・仮説検証の反復が必要 |
| デザイン刷新の企画・配色/レイアウトの意思決定（`design-best-practices`併用時） | Opus | 事例に基づく判断や複数案の比較検討が要る |
| 通常の実装・バグ修正・PRレビュー対応・コミット/プッシュ | Sonnet（標準・デフォルト） | 大半の開発作業はここで十分。無理にOpusへ上げない |
| 単純なファイル検索・特定文字列の有無確認・定型フォーマットチェック | Haiku（軽量） | 判断の余地がほとんどない定型作業 |
| CIステータスの機械的な確認、単純な繰り返しの動作確認 | Haiku | 同上 |

サブタスク単位で使い分けたい場合は `Agent` ツールの `model` パラメータでモデルを指定する
（例: 単純な繰り返し調査は `model: "haiku"` で投げ、複雑な分析は指定なし/`"opus"`のまま）。
`Explore` エージェントは元々読み取り専用の軽い探索用なので、単純なファイル特定にはこちらを
優先し、独自にファイルを総当たりで`Read`しない。

**実測での注意点**: `ls`一発のような極小タスクをHaikuサブエージェントに投げて検証した
ところ、サブエージェント自体の起動（システムプロンプト・ツール定義の読み込み等）だけで
約4万トークンを消費した。軽いモデルに逃がすこと自体は無料ではなく、`Agent`を1回起動する
オーバーヘッドがある。したがって「Haikuなら安い」と短絡せず、**その作業がサブエージェント
起動コストを上回る規模・独立性を持つか**を先に判断する。1コマンドで終わるような処理は
サブエージェントに投げず、メインセッションで直接`Bash`/`Grep`/`Glob`を使う方が安い。

## セッションを長持ちさせるための行動

- [ ] 大きいファイルはいきなり`Read`せず、まず`Grep`/`Glob`で当たりを付ける
- [ ] 使う予定のないツール定義を先読みしない（`ToolSearch`で必要な時にだけ取得する構成を維持）
- [ ] 無関係な新しいテーマの作業は、今のセッションを引き伸ばさず新しいセッション/ブランチ/PRに分ける
- [ ] CLAUDE.mdやスキルなど安定していてよい大きな内容は、必要がない限り書き換えない（プロンプト
      キャッシュを効かせ続けるため）
- [ ] 独立して進められる調査・実装は`Agent`(`run_in_background: true`)に逃がし、メインの会話で
      ポーリング待ちをしない（通知が来たら続きをやる）
- [ ] 自動化・監視ループ（PR監視、Routineでのチェックインなど）には必ず終了条件と現実的な間隔を
      設定し、進捗のない繰り返しを続けない（AutoGPTの教訓）
- [ ] 1回の`Read`で長大なログ・生データを丸ごと会話に持ち込まず、必要な要約や該当箇所だけを
      抜き出す
- [ ] **PR監視はWebhook購読（イベント駆動）とポーリング用チェックイン（`send_later`等での
      定期起床）を混同しない。** Webhook購読はコメント・レビュー・マージなど実際に何か
      起きた時だけセッションを起こすのでコストはほぼゼロ。一方、時間指定の定期チェックインは
      何も起きていなくても強制的にセッションを再起動しトークンを消費する。CIが設定されておらず
      自動レビュアーもいないPR（ドキュメントのみの変更など）では、定期チェックインを追加せず
      Webhook購読だけに任せる。定期チェックインを使うのは「Webhookが確実に来ない変化」
      （CI成功・マージ衝突などの取りこぼしやすいイベント）を補う必要があるときに限る。

## この振り返りタスクについての前提

Claude Codeには過去セッションのトークン数・コストを遡って集計するツールがない。そのため
「過去のどの発言が高コストだったか」を実測で特定することはできない。このスキルは、代わりに
一般的な無駄遣いパターンを恒久ルール化し、以後のセッションで自動的に効くようにするための
ものである。
