# 01. 製品設計 ― 「自動売買ツール」の形を決める

「自動」の意味を最初に固定する。**完全自動発注ではなく、LINEにシグナルを
送るだけの半自動**を採用する（ユーザー選定）。理由：

| 比較項目 | LINE通知のみ | 証券会社API経由の完全自動発注 |
|---|---|---|
| 実装コスト | 低い（判定ロジック＋通知だけ） | 高い（`fx/fxbot/` 相当の執行層が必要） |
| リスク | 最終判断はユーザー（誤発注しない） | 誤発注・二重発注のリスクを自前で潰す必要 |
| 規制・審査 | 不要 | 証券会社のAPI利用審査が必要な場合あり |
| 実運用への距離 | 最短 | 最長 |

**まず判定ロジックの正しさを実運用で確かめ、信頼できてから自動発注に
進む**という段階を踏む。これは[FXの設計](../../fx/README.md)で
「Phase 1は検証、Phase 2でデモ、Phase 3で最小ロット」と段階を踏んだのと
同じ考え方。LINE通知フェーズが、この製品におけるPhase 1〜2に相当する。

## 1. 全体構成

```
                日次バッチ(1日1回、取引時間後)
                        │
      ┌─────────────────┼─────────────────┐
      ▼                 ▼                 ▼
  価格取得           シグナル計算        前回状態の読み込み
 (レバ型ETF/         (value_averaging.py    (直前の目標価値・
  投信の基準価額)      のロジックを流用)      保有株数)
      │                 │                 │
      └─────────────────┼─────────────────┘
                        ▼
                 「買い/売り/様子見」判定
                        │
                        ▼
                 LINE Messaging API
                        │
                        ▼
                  ユーザーのLINE
                 (受け取って手動発注)
                        │
                        ▼
              発注結果をどこかに記録
           (次回バッチの「前回状態」に反映)
```

**バックテストと本番判定が同じロジックを使うこと**が最重要
（FXの`fx1.py`と`fxbot/`が同じ戦略関数を共有するのと同じ設計判断）。
`value_averaging.py` の `simulate()` を1期間だけ進める形に切り出し、
本番判定でも同じ関数を呼ぶ。

## 2. なぜ「売却なし・バリュー平均法」を軸にするか

[README](../README.md) の検証結果より、資産クラスの構造（ボラティリティ
減衰）と噛み合うのは「売却なし」版。利確による上値キャップがなく、
下落時の買い増しだけを行う。これなら:

- シグナルは基本的に「買い増し額」の通知だけで済む（売り指示が要らない）
- 上限（基準拠出額の5倍）に達した回だけ「通常より多い金額が必要」と
  警告すればよく、判断がシンプル

ただし [README](../README.md) の「次にやること」6番のとおり、
成長率g・基準拠出額Cのパラメータ感度はまだ確認していない。
実運用の判定ロジックとして固定する前に、`param_sweep.py`と同じ手順で
確認する必要がある。

## 3. データ取得 ― ここが本番運用の最大の壁

これまでの検証はすべて**過去の静的ファイル**（`nikkei225_close.parquet`）
に対するバックテストだった。LINE通知を毎日送るには、**「今日」の価格を
毎日取得できる経路**が要る。これは新しい要件で、まだ検証していない。

候補（優先順）:

| 経路 | 長所 | 短所 |
|---|---|---|
| 対象ETF（例:1570）の日次終値をブラウザ操作 or スクレイピングで取得 | 実際の売買対象の値そのもの | 利用規約の確認が必要。サイト構造変化に弱い |
| J-Quants API（JPX公式・個人無料プラン） | 公式・安定 | 登録が要る（[06-Phase1実行記録](../../fx/docs/06-Phase1実行記録.md)でのOANDA同様、後回しにできる） |
| 証券会社の株価取得API（楽天証券など） | 発注先と同じ経路で一貫 | 口座開設・API利用登録が要る |

FXの`fx1.py`と同様、**まずは無料・登録不要の経路で判定ロジックを検証し、
運用直前にJ-Quants等の安定した経路に切り替える**方針が合理的。
このコンテナのネットワークポリシーでは主要な経路が軒並み遮断されていた
（[fx/docs/06-Phase1実行記録.md §5](../../fx/docs/06-Phase1実行記録.md)
参照）ため、実装はローカル環境で行う前提とする。

## 4. LINE通知の実装 ― LINE Notifyは終了済み

**LINE Notifyは2025年3月31日にサービス終了。** 現在の唯一の経路は
**LINE Messaging API**（個人用のLINE公式アカウントを作成し、そこから
自分のLINEへメッセージを送る）。

| 項目 | 内容 |
|---|---|
| 必要な準備 | LINE公式アカウント開設（無料）→ Messaging APIのチャネル作成 → チャネルアクセストークン発行 → 自分のLINEをそのアカウントと友だち登録 |
| 送信方法 | チャネルアクセストークンを使い、`push message` APIをHTTPで呼ぶ（言語問わず、`requests`等で数行） |
| 料金 | 無料枠は月200通。日次通知（月20〜22通）なら余裕で収まる |
| 通知内容の例 | 「【日経レバ】本日の判定: 買い増し ¥12,340（基準額の1.2倍）現在の目標乖離: -8.3%」 |

### メッセージ設計の指針

判断に必要な情報を過不足なく：

```
【日経レバ・バリュー平均法】2026-XX-XX
判定: 買い増し
金額目安: ¥XX,XXX（基準額の X.X倍）
現在の評価額: ¥XXX,XXX（目標比 XX%）
※上限到達時は「通常の5倍が上限です」等の注記を追加
```

「様子見」の日も**毎日送るか、動きがあった日だけ送るか**は運用しながら
決める。何も起きない日に毎日通知が来ると煩わしくなり、見落としの原因に
なりうる（FXの「アラート疲れ」と同じ問題）。

## 5. Codexとの相談について

このセッションからは `api.openai.com` への到達性と `OPENAI_API_KEY` が
未設定のため、Codex CLIとの相談ができなかった。次回セッションで相談する
場合の準備:

1. claude.ai/code の環境設定を開く（メッセージボックス上の雲アイコン）
2. 対象環境の歯車アイコン → **Network access** を `Custom` に変更し、
   **Allowed domains** に `api.openai.com` を追加
   （「Also include default list of common package managers」に
   チェックを入れておくとnpm等が引き続き使える）
3. **Environment variables** に `OPENAI_API_KEY=sk-...` を追加
   （[運用上の注意]: クラウド環境の環境変数は秘密情報ストアではないと
   公式ドキュメントに明記されている。個人用途と割り切るか、
   ローカル環境でのCodex利用に切り替えるかを検討する余地がある）
4. 上記の変更は**次回以降に開始したセッションから**反映される
