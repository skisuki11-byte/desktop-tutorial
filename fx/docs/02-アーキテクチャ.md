# 02. アーキテクチャ

[01-目標とリスク設計](01-目標とリスク設計.md) の結論から、システムに要求される機能が決まる。

| 01の設計判断 | アーキテクチャへの要求 |
|---|---|
| ① 年利ではなくシャープで管理 | 目標年率ボラを設定値として外出しし、戦略コードから切り離す |
| ③ 段階的にボラを上げる | ボラターゲティング層を戦略層と独立させる |
| ⑤ 相関を見て戦略を追加 | 戦略を差し替え可能な純関数にし、相関行列を常時算出する |
| ⑥ レバ上限10倍 | サイジング層でレバレッジ上限を強制する |
| 03の試行回数登録 | 戦略レジストリに検証履歴を残す |

## 1. 2つの実装を使い分ける（Notionの方針を継承）

|  | `fx1.py`（簡易版） | `fxbot`（フルセット） |
|---|---|---|
| 規模 | 1ファイル・約100行 | レイヤー分離 |
| 用途 | エッジを探す（**いまここ**） | デモ・実弾運用 |
| 持つもの | ベクトル化した損益計算だけ | 冪等な発注、リコンサイル、キルスイッチ、全判断ログ |

実際にお金が動くまでフルセットの機能は要らない。
逆に、お金が動き始めたら簡易版では確実に事故る。

**ただし、両者は同じ戦略関数を読み込む。** これが唯一の設計上の約束事。
検証したコードと運用するコードが別物になった瞬間、検証結果は意味を失う。

## 2. レイヤー構成

```
                     ┌──────────────┐
   価格データ ──────▶│  strategies  │  純関数。ポジション比率 -1〜+1 を返す
                     └───────┬──────┘  ※ 資金・ロット・口座を一切知らない
                             │ signals (DataFrame: 時刻 × 戦略)
                     ┌───────▼──────┐
                     │  portfolio   │  戦略間の配分。相関・共分散を推定
                     └───────┬──────┘
                             │ weights
                     ┌───────▼──────┐
                     │     risk     │  ボラターゲティング / レバ上限 / DDガバナー
                     └───────┬──────┘
                             │ target_positions（通貨量）
              ┌──────────────┴──────────────┐
              ▼                             ▼
      ┌───────────────┐            ┌────────────────┐
      │   backtest    │            │   execution    │
      │ 過去で回す     │            │ 実際に発注する  │
      └───────┬───────┘            └────────┬───────┘
              │                             │
              └────────────┬────────────────┘
                           ▼
                    ┌─────────────┐
                    │   journal   │  全判断のログ。後から «なぜその発注をしたか» を再現できる
                    └─────────────┘
```

**backtest と execution が同じ `target_positions` を受け取る**のが要点。
検証と運用の分岐点をできるだけ下流に置くことで、両者のズレを構造的に防ぐ。

## 4. インターフェース定義

設計上いちばん重要な3つの境界。ここさえ守れば中身は差し替えられる。

### 4.1 Strategy ― ポジション比率を返す純関数

```python
# fxbot/strategies/base.py
from typing import Protocol
import pandas as pd

class Strategy(Protocol):
    name: str
    params: dict

    def positions(self, df: pd.DataFrame) -> pd.Series:
        """価格DataFrameを受け取り、-1.0〜+1.0 のポジション比率を返す。

        制約（これを破ると検証が無意味になる）:
          - 時刻 t の出力は、t 以前の情報だけで決まること
          - 資金額・ロット数・口座・レバレッジを一切参照しないこと
          - 副作用を持たないこと（同じ入力なら常に同じ出力）
        """
```

**なぜ「比率」なのか** ― 戦略がロット数を返すと、
資金管理とエッジの判定が混ざる。相関の計算もできなくなる。
「どちらにどれだけ傾くか」だけを戦略が決め、
「いくら賭けるか」は risk 層が一元的に決める。

**なぜ純関数なのか** ― 01の設計判断⑤で、戦略は相関を見ながら
足したり抜いたりする。状態を持つと差し替えが事故になる。

### 4.2 Allocator ― 戦略間の配分

```python
# fxbot/portfolio/allocator.py
def allocate(
    signals: pd.DataFrame,      # 時刻 × 戦略 のポジション比率
    cov: pd.DataFrame,          # 戦略リターンのEWMA共分散
    method: str = "equal_risk",
) -> pd.Series:
    """各戦略へのウェイトを返す（合計1.0）。

    equal_risk: 各戦略のリスク寄与を均等化。相関が高い戦略は自動的に軽くなる
    equal_weight: 単純等分。戦略数が少ないうちはこちらが頑健
    """
```

戦略数が5本未満のうちは `equal_weight` を使う。
共分散の推定誤差のほうが、最適化で得られる改善より大きくなるため。

### 4.3 RiskLayer ― 目標ボラとレバレッジ上限

```python
# fxbot/risk/vol_target.py
def size(
    combined_position: pd.Series,   # 配分後の合成ポジション比率
    realized_vol: pd.Series,        # 20営業日EWMAの実現年率ボラ
    target_vol: float,              # config/risk.yaml。初期0.30
    max_leverage: float = 10.0,     # 01の設計判断⑥
    equity: float = 1_000_000,
) -> pd.Series:
    """通貨量（建玉）を返す。

    scale = target_vol / realized_vol   をポジションに掛ける
    そのうえで実効レバレッジが max_leverage を超えないようクリップする。

    ボラが下がると自動で建玉が増えるため、クリップは必須。
    2024年のような低ボラ局面で無制限にレバが上がり、
    ボラ回帰で一発退場する ―― これが典型的な壊れ方。
    """
```

> **この層があるおかげで、「年利40%を狙う／年利25%で安全に走る」の切り替えが
> `target_vol` の1行変更で済む。** 01の設計判断③がここで実装される。

## 5. データ設計

### 5.1 スキーマ

parquet 1ファイル、bid/ask を両方持つ。**mid だけ保存しない。**
mid にするとスプレッドが検証から消え、成績が過大評価される。

| 列 | 型 | 備考 |
|---|---|---|
| `ts` | timestamp[UTC] | 足の開始時刻。tz-aware で保存 |
| `bid_o/h/l/c` | float64 | |
| `ask_o/h/l/c` | float64 | |
| `volume` | int64 | ティック数（業者による） |

### 5.2 データソース

| フェーズ | ソース | 備考 |
|---|---|---|
| Phase 1 | HistData（無料・M1） | mid のみ。`import_histdata.py` の `SpreadModel` で bid/ask を合成 |
| Phase 2以降 | OANDA v20 `price=BA` | 実スプレッド。`fetch_oanda.py` |

HistData を使う間、バックテスト結果は
**「スプレッド前提が正しければ」という条件付きの数字**であることを忘れない。
迷ったら広めに設定する。狭く見積もると、存在しないエッジがあるように見える。

### 5.3 取得範囲

**10年分（2016年〜）を取る。** 5年ではなく10年。
[03-検証プロトコル](03-検証プロトコル.md) の選択バイアス足切りラインが、
5年で1.13、10年で0.80と大きく変わるため。取得コストはゼロ。

期間には2016年（トランプ相場）、2020年（コロナ）、2022年（急激な円安）、
2024年（日銀利上げ）が含まれる。レジームの多様性そのものが検証価値になる。

## 6. 死守すべき2点（Notionから継承）

他は全部省いてよい。ここだけは絶対に省略しない。

### ① ポジションを1本ずらす（shift）

ずらさないと、同じ足の終値で判断して同じ足で約定したことになる。
未来を見て取引したのと同じ。

### ② ポジションが動いた足でスプレッドを払わせる

忘れると、どんなノイズでも儲かって見える。

### 実測した差

エッジが存在しないランダムウォークデータでブレイクアウト戦略を検証した結果：

| 条件 | 損益（円／1万通貨） |
|---|---|
| 正しく1本ずらす | **-22,233** |
| ずらさない（未来参照） | **+211,444** |

エッジがゼロのデータで20万円の利益が出る。
個人のバックテストが実運用で崩壊する原因の筆頭がこれ。

```python
def backtest(df, pos, spread_pips=1.0):
    pos  = pos.shift(1).fillna(0.0)                        # ★1 未来参照の防止
    ret  = df["close"].diff() * pos
    cost = pos.diff().abs().fillna(0) * spread_pips * PIP  # ★2 売買コスト
    pnl  = ret - cost
    return pnl, pnl.cumsum(), pos
```

### 検算

ダミーのランダムウォークで回すと **必ず負けるのが正しい**
（スプレッドとスリッページの分だけ削られる）。
実測は PF 0.31／260トレード／総リターン -11.96%。

**ここで勝ってしまったら、未来参照かコスト未計上のバグがある。**

## 7. 実行系の設計（Phase 2以降）

お金が動き始めてから必要になるもの。Phase 1 では作らない。

| 機能 | なぜ必要か |
|---|---|
| **冪等な発注** | ネットワーク再送で同じ注文が2回通ると、想定の2倍の建玉になる。`clientOrderId` で業者側に重複排除させる |
| **起動時リコンサイル** | プロセス再起動後、ローカルの想定建玉と口座の実建玉を突合。ズレていたら発注せず停止して通知 |
| **キルスイッチ** | 日次損失上限・連続損失・スプレッド異常・データ遅延で強制フラット化 |
| **全判断ログ** | 「なぜこの時刻にこの建玉にしたか」を後から再現。入力価格・シグナル・ウェイト・実現ボラ・スケール・最終建玉をJSONLで残す |

### 状態遷移

```
起動 ─▶ リコンサイル ─┬─ 一致 ─────▶ RUNNING ─┬─ 通常 ─▶ 発注
                     │                        │
                     └─ 不一致 ─▶ HALTED      ├─ DDガバナー発動 ─▶ REDUCED（レバ減）
                                 （手動解除）  │
                                              └─ キルスイッチ ─▶ FLAT（全決済・停止）
```

`HALTED` からの復帰は **必ず手動**。
自動復帰させると、原因不明のズレを抱えたまま発注を再開してしまう。

## 8. 設定ファイル

戦略コードに数字を埋め込まない。運用中に変えるものは全てYAMLへ。

```yaml
# fxbot/config/risk.yaml
target_vol: 0.30          # 年率。01の設計判断③。実測S次第で 0.20〜0.40 を動かす
max_leverage: 10.0        # 01の設計判断⑥
vol_lookback_days: 20     # 実現ボラのEWMA半減期

governor:                 # DDに応じてレバレッジを落とす
  - {drawdown: 0.10, scale: 0.70}
  - {drawdown: 0.15, scale: 0.50}
  - {drawdown: 0.20, scale: 0.30}
  - {drawdown: 0.30, scale: 0.00}   # 全停止・再検証

killswitch:
  daily_loss_pct: 0.05    # 1日で資金の5%失ったら停止
  consecutive_losses: 10
  max_spread_pips: 5.0    # これを超える環境では新規建てしない
  data_staleness_sec: 120 # 足が2分来なければ停止
```

`governor` の閾値は 01 のDD分布から決めている。
S=1.5・ボラ30%運用でDD中央値19.0%、90%点29.8%。
つまり **DD20%は「よくあること」で、DD30%は「めったにない」**。
20%で止めると正常な変動で運用が終わってしまい、
30%まで放置すると異常を見逃す。だから段階的に落とす。
