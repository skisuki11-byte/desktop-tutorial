# 03. 検証プロトコル

[01](01-目標とリスク設計.md) で「ネットシャープ1.5以上の束を作る」と決めた。
この文書は **その数字を信じてよいかどうかを判定する手続き** を定める。

前提として、バックテストのシャープは **ほぼ必ず実運用より高く出る**。
理由は3つあり、それぞれに対策が要る。

| 過大評価の原因 | 対策 | 節 |
|---|---|---|
| 未来参照・コスト未計上 | shift とスプレッドの強制。ランダムウォークで検算 | [02の6節](02-アーキテクチャ.md) |
| パラメータの過剰最適化 | ウォークフォワード＋感度分析 | §2, §4 |
| **選択バイアス（たくさん試した）** | **試行回数の登録とDSR足切り** | **§3** |

3つめが最も強力で、最も見落とされる。

## 1. データの分割

10年分（2016–2026）を次のように使う。

```
├──────────── IS 6年 ────────────┼─ OOS 3年 ─┼─ 封印 1年 ─┤
  2016      開発・パラメータ探索   2022        2025      2026
```

| 区間 | 用途 | ルール |
|---|---|---|
| **IS（In-Sample）6年** | 戦略の発想・パラメータ探索 | 何度見てもよい |
| **OOS 3年** | 採用判定 | **1戦略につき1回だけ**回す。回した回数を記録する |
| **封印 1年** | 最終確認 | 束が完成し、Phase 2 に進むと決めた時点で **1回だけ** 開ける |

封印区間を最後まで触らないことが、この手続き全体の担保になる。
OOSを何度も見れば、それは実質的にISになる。

## 2. ウォークフォワード分析

単一の IS/OOS 分割だけでは、たまたま相性のよい期間を引いた可能性を排除できない。
IS区間の内部でローリングのウォークフォワードを回す。

```
学習 24ヶ月 → 検証 6ヶ月 → 6ヶ月ずらす → 繰り返し
```

| 設定 | 値 |
|---|---|
| 学習窓 | 24ヶ月（ローリング。アンカーではない） |
| 検証窓 | 6ヶ月 |
| ステップ | 6ヶ月 |
| 区間数 | 約8区間（IS 6年） |

**判定に使う数字は、全区間の検証窓をつないだ「WF合成曲線」**。
学習窓の成績は一切見ない。

### エンバーゴ

学習窓と検証窓の間に **5営業日の空白** を置く。
指標系・スイング系の戦略は保有期間が数日に及ぶため、
境界をまたぐポジションが情報を漏らす。

## 3. 選択バイアスと足切りライン（最重要）

戦略を100本試して最良の1本を選べば、そのシャープには
「たくさん試したこと」による下駄が乗っている。

真のシャープがゼロの戦略を n 本試したときの、最良バックテストシャープの期待値：

```
E[max SR] ≈ √V · [ (1-γ)·Φ⁻¹(1 - 1/n) + γ·Φ⁻¹(1 - 1/(n·e)) ]
    V = 1/T（T は検証年数）,  γ = 0.5772（オイラー定数）
```

| 検証年数 | 10本試行 | 30本試行 | 100本試行 | 300本試行 | 1000本試行 |
|---|---|---|---|---|---|
| 3年 | 0.91 | 1.20 | 1.46 | 1.67 | 1.88 |
| **5年** | 0.70 | 0.93 | **1.13** | 1.29 | 1.46 |
| **10年** | 0.50 | 0.66 | **0.80** | 0.92 | 1.03 |
| 20年 | 0.35 | 0.46 | 0.57 | 0.65 | 0.73 |

**これ以下のシャープは、エッジがゼロでも普通に出る。**

読み方の例：5年データで100本試して見つけたシャープ1.1の戦略は、
**何の成果でもない**。同じ戦略を10年データで検証してシャープ1.1が残るなら、
足切り0.80を超えているので意味を持つ。

### なぜこれが致命的か

01の設計判断⑤で「相関の低い戦略を8本集める」と決めた。
8本集めるには何十本、何百本と試すことになる。
**目標を達成しようとする行為そのものが、選択バイアスを膨らませる。**

### 運用ルール

1. **試行回数を必ず記録する。** `fxbot/strategies/registry.py` に、
   検証した戦略・パラメータ組合せを1件ずつ追記する。
   パラメータグリッドを回した場合は **グリッドの点数を試行回数に数える**
   （20通り試したら20本）。
2. 記録した累計試行回数 n と検証年数 T から足切りラインを算出し、
   **OOSシャープがそれを超えた戦略だけ採用する。**
3. 「なんとなく回してみた」も1本に数える。数え漏らすと足切りが甘くなり、
   自分を騙すことになる。

### レジストリの記録項目

| 項目 | 例 |
|---|---|
| `trial_id` | 通し番号 |
| `date` | 2026-08-24 |
| `strategy` | nakane |
| `params` | `{"start": 900, "end": 955}` |
| `grid_size` | 1（グリッド探索なら点数） |
| `data_range` | 2016-01-01 〜 2021-12-31（IS） |
| `is_sharpe` | 0.82 |
| `oos_sharpe` | 未実行 / 0.61 |
| `oos_runs` | 0 → 1（OOSを回した回数。2以上は警告） |

## 4. 個別戦略の採用ライン

**検証を始める前に固定した基準。後から緩めない。**
緩める場合は「いつ・なぜ緩めたか」をレジストリに記録する。

| # | 基準 | 根拠 |
|---|---|---|
| 1 | WF合成の取引回数 **200以上** | 統計的に意味を持つ最低本数（Notion踏襲） |
| 2 | **OOSシャープ > DSR足切りライン** | §3。試行回数から算出 |
| 3 | OOS **PF 1.2以上** | Notion踏襲 |
| 4 | **最良の1年を除いても年次リターンが正** | 単年依存の排除。Notionの「特定の1年に偏っていない」を機械判定に落としたもの |
| 5 | **スプレッド1.5倍でPF 1.0以上** | HistDataの合成スプレッドは楽観的。実勢で崩れる戦略を落とす |
| 6 | **パラメータ ±20% でシャープが半減しない** | 過剰最適化の検出。きれいな右肩上がりほど疑う |
| 7 | **既存の束との相関が0.4以下** | 01の設計判断⑤。単体成績がよくても相関が高ければ不採用 |

基準6の補足 ― パラメータを少し動かして崩れるなら偽物。
最適値が「山の頂上」ではなく「高原の上」にあることを確認する。

## 5. 束（ポートフォリオ）の採用ライン

個別戦略が通っても、束として目標に届かなければ意味がない。

| # | 基準 | 根拠 |
|---|---|---|
| 1 | 合成 **OOSネットシャープ 1.0以上** | Phase 2 に進むゲート（[README](../README.md)） |
| 2 | 戦略間の **平均相関 0.3以下** | 01 §5。0.3を超えると本数を増やしても伸びない |
| 3 | 目標ボラ運用時の **実効レバレッジが10倍以下** | 01の設計判断⑥ |
| 4 | モンテカルロDD 90%点が **資金の35%以内** | 01 §3。ボラ30%運用の想定29.8%＋余裕 |
| 5 | 稼働率が **25%以上** | 01 §6。低稼働だとレバ上限に張り付く |

## 6. モンテカルロ検証

WF合成曲線が1本きれいでも、それは1つの実現パスにすぎない。
次の2つを回して、成績の分布を見る。

### 6.1 トレード順序シャッフル

WF合成で得たトレード損益列をランダムに並べ替え、10,000パス生成する。

- 見るもの：**最大DDの分布**（90%点・99%点）
- 目的：「たまたま良い順番で並んでいた」のを剥がす。
  実現DDが分布の下位にあるなら、運用中に今回より深いDDが普通に来る。

### 6.2 ブロックブートストラップ

日次リターンを **20営業日のブロック単位** でリサンプリングする。
1日単位で混ぜると自己相関が壊れ、リスクを過小評価する。

- 見るもの：**シャープの信頼区間**
- 判定：シャープの5%点が **0を下回るなら不採用**。
  点推定が1.5でも、区間が [-0.2, 3.2] なら何も言えていない。

## 7. 検証を通したあと必ずやること：ランダムウォーク検算

新しい検証コードを書いたら、**必ずダミーのランダムウォークで回す。**

| 期待される結果 | 意味 |
|---|---|
| 負ける（PF 1.0未満） | 正常。スプレッド分だけ削られている |
| 勝つ | **バグがある。** 未来参照かコスト未計上を疑う |

実測基準値：PF 0.31／260トレード／総リターン -11.96%。

## 8. 避けるべき失敗パターン（Notionから継承）

| パターン | なぜ危険か |
|---|---|
| **過剰最適化** | きれいな右肩上がりほど疑う。パラメータを少し動かして崩れるなら偽物 |
| **ナンピン・マーチン系** | 勝率95%でも一発で退場。バックテストでは超優秀に見えるのが厄介 |
| **手数料・スリッページ無視** | 小さなエッジは実運用コストで簡単に消える |
| **OOSの再利用** | 2回目以降のOOSはISと同じ。レジストリの `oos_runs` で検出する |
| **不合格を「惜しかった」と読む** | 基準は事前に決めてある。境界線上は不合格 |

## 9. 進め方

```
1. データ取得（10年・USD/JPY M5）
2. ランダムウォーク検算 ─── 勝ったらバグ。ここで止める
3. 仲値アノマリーを IS で検証 ── レジストリに記録
4. WF回して合成曲線を作る
5. 採用ライン §4 と照合
     ├─ 合格 → OOSを1回だけ回す → 束に追加
     └─ 不合格 → 次の仮説へ（レジストリに試行として記録）
6. 3〜5を繰り返し、相関0.3以下で束を育てる
7. 束が §5 を満たしたら、封印区間を1回だけ開ける
8. 通れば Phase 2（デモ運用）へ
```

**1本目で不合格でも失敗ではない。** 検証基盤が正しく機能していることの確認になる。
むしろ1本目であっさり合格したときのほうが、バグを疑うべき。
