## 1. データ取得 ― 遠回りになった

このコンテナのネットワークは **Trusted** ポリシーで、FXデータの配信元が軒並み塞がれている。
実測した到達性：

| ホスト | 結果 |
|---|---|
| `www.histdata.com` | ✗ 遮断 |
| `query1.finance.yahoo.com` | ✗ 遮断 |
| `stooq.com` / `api.frankfurter.app` / `www.alphavantage.co` | ✗ 遮断 |
| `fred.stlouisfed.org` / `api.tiingo.com` | ✗ 遮断 |
| **`raw.githubusercontent.com`** | **○ 到達可** |
| `pypi.org` | ○ 到達可 |

PyPIのパッケージ（yfinance・histdata・forex-python）はいずれも
**実行時に遮断先を叩く**ので使えない。

公開リポジトリの committed ファイルは security proxy 経由で配信される仕様
（`raw.githubusercontent.com` はTrustedの既定リストに含まれる）。
そこから [ejtraderLabs/historical-data](https://github.com/ejtraderLabs/historical-data)
の USD/JPY を取得した。

|---|---|---|
| 足の長さ | **M15** | M5 |

## 2. タイムゾーンの特定 ― ここを間違えると全部無意味になる

取得したCSVの時刻はタイムゾーン未記載だった。
仲値アノマリーは **JST 9:00〜9:55 という55分の窓**なので、
1時間ずれれば別の時間帯を検証したことになる。推測せず実測した。

### 手がかり1: 曜日と週境界

土日のバーがゼロ、月曜00:00開始、金曜23:xx終了。
これはMT5のEETサーバー時刻の週境界（日曜17:00 NY = 月曜00:00 EET）と一致する。

### 手がかり2: ティック出来高の日内プロファイル

| データ上の時刻 | 出来高 | 対応する市場 |
|---|---|---|
| 3時 | 1,028 | 東京オープン（00 UTC） |
| 10時 | 1,182 | ロンドンオープン（08 UTC） |
| 15-17時 | 1,289〜1,502 | NY・ロンドン重複（13-15 UTC） |

すべて **UTC+2** で整合する。

### 手がかり3: 夏時間があるか

月別に「早朝の出来高ピークが何時に出るか」を測った。

| 月 | ピーク | 判定 |
|---|---|---|
| 1, 2, 11, 12月 | **2時** | 冬時間（EET, UTC+2） |
| 4〜10月 | **3時** | 夏時間（EEST, UTC+3） |
| 3, 10月 | 混在 | 切替月 |

**夏時間が実在する。固定オフセットで変換してはいけない。**
`Europe/Athens`（EU夏時間規則）でローカライズしてUTCに変換した。

### 変換後の検算

JST基準の出来高プロファイルで、3つの市場オープンが正しい時刻に立つことを確認：

| 市場 | JST | 直前比 | 判定 |
|---|---|---|---|
| 東京オープン | 9時 | 1.64倍 | ○ |
| ロンドン | 16時 | 1.58倍 | ○ |
| NY | 22時 | 1.68倍 | ○ |

この検算は `import_ejtrader.py` に組み込んであり、毎回自動で走る。

### 検算ロジック自体のバグも1つ見つけた

最初、欠損検出のしきい値を36時間にしていたところ **489箇所** が検出された。
9.3年は約484週末なので、**週末そのものを全部拾っていた**。
EETサーバーの週末ギャップは金23:45→月00:00で約48時間ある。
60時間に直すと本当の穴は **6箇所** だけで、すべて年末年始だった。データ品質は良好。

## 3. 足の長さに依存しない形への修正

`breakout` のパラメータを **本数** で持っていたのは誤りだった。
`n=288` はM5なら1日だが、M15では3日になる。**データを替えると別の戦略になる。**

窓を **日数** で持ち、`load()` で検出した足の長さから本数を計算する形に直した。

```python
def breakout(df, days: float = 1.0):
    n = max(2, int(round(days * bars_per_day(df))))
```

グリッドも `[0.25, 0.5, 1.0, 2.0, 4.0]` 日に変更。

## 4. 仲値アノマリー ― 存在しなかった

M15では建玉が立つのは JST 9:00 / 9:15 / 9:30 / 9:45 の4本。
2,401日ぶん、稼働率4.17%。取引1,801回。

| 項目 | 値 |
|---|---|
| ネット総リターン | **-25.67%** |
| うち売買コスト | -17.74% |
| **グロス（コスト前）** | **-7.93%** |
| グロスのシャープ | **-0.45** |

**コストで消えているのではない。グロスの時点で負けている。**
「アノマリーはあるが手数料で取れない」ではなく、**方向そのものが無い**。

### 年別グロス（経年変化）

| 年 | グロス | ネット |
|---|---|---|
| 2013 | -5.47% | -7.59% |
| 2016 | -2.93% | -4.85% |
| 2017 | +0.41% | -1.43% |
| 2018 | +1.08% | -0.78% |
| 2020 | -1.25% | -3.19% |
| 2021 | +1.79% | -0.11% |

正の年も負の年もあり、一貫した傾向がない。
建玉を反転しても（ショート版）シャープ -0.56 で、どちらの向きにもエッジはない。

### 採用ライン照合

| # | 基準 | 結果 |
|---|---|---|
| 1 | 取引回数 200以上 | ○ 1,801 |
| 2 | シャープ下限 > 足切り(0.00) | **× -1.68** |

| 6 | パラメータ±20%で半減しない | ○ 対象外 |
| 7 | ブートストラップ5%点 > 0 | **× -1.76** |

ブートストラップでシャープが負になる確率 **100.0%**。疑う余地がない。

## 5. ブレイクアウト ― 雑音と区別できない

ウォークフォワード（学習24ヶ月／検証6ヶ月／エンバーゴ5営業日）で
`days` を5点探索。最頻採用は2.0日。

| # | 基準 | 結果 |
|---|---|---|
| 1 | 取引回数 200以上 | ○ 613 |
| 2 | シャープ下限 > 足切り(0.44) | **× 0.07** |
| 3 | PF 1.2以上 | **× 1.19** |
| 4 | 最良年を除いても正 | ○ +7.67% |
| 5 | スプレッド1.5倍でPF 1.0以上 | ○ 1.281 |
| 6 | パラメータ±20%で半減しない | ○ 87% |
| 7 | ブートストラップ5%点 > 0 | **× -0.10** |

シャープ 0.42 ± 0.36。ブートストラップの中央値0.44、5%点 -0.10、
シャープが負になる確率 8.8%。

**わずかに正だが、雑音と区別できない。**

PF 1.19 は基準1.2 をわずか0.01下回る。ここで緩めたくなるが、緩めない。

## 6. 何が言えて、何が言えないか

### 言えること

- **仲値アノマリーは 2012-2022 のUSD/JPYには存在しない。** グロスで負けている以上、
  スプレッド前提や執行の巧拙の問題ではない
- ブレイクアウトは同期間でわずかに正だが、統計的に有意ではない
- 検証基盤は実データでも壊れなかった（欠損検出・時刻変換の検算がすべて通った）

### 言えないこと

- **2022〜2025年については何も言えない。** データが2022年3月で終わっている。
  この期間はUSD/JPYが115円から160円へ動いた特異な局面で、
  トレンド系が有利だった可能性がある
- M5でどうなるかは分からない。仲値の窓（9:55のフィキシング）を
  M15より細かく狙えれば結果が変わりうる
- 実スプレッドでどうなるかは分からない。合成スプレッドでの結果

## 7. 2022〜2026年を埋める ― 日次データでの追加検証

§6で「2022〜2025年については何も言えない」と書いた穴を、別のデータで部分的に埋めた。

### 到達可能な経路をもう一度洗った

| ホスト | 結果 |
|---|---|
| `raw.githubusercontent.com` | ○ |
| `pypi.org` / `api.github.com` | ○（ただしAPIはリポジトリスコープが強制され未接続は403） |
| **`codeload.github.com`** | ○（リポジトリのtarball） |
| **`objects.githubusercontent.com`** | ○（リリース資産の配信先） |
| `drive.google.com` | ✗ |

`philipperemy/FX-1-Minute-Data`（HistData由来のM1）はデータ本体が
**Google Drive（3GB）**にあり、そこは遮断されている。
リリースAPIも未接続リポジトリでは403。この経路は使えなかった。

代わりに [datasets/exchange-rates](https://github.com/datasets/exchange-rates)
（FRB H.10 由来の日次レート）を取得した。**2026-08-14まで更新されている。**

### このデータでできないこと（先に書く）

1. **取引可能な価格ではない。** FRBが公表する参照レート（正午買値）であって
   約定できるレートではない。「そういう値動きだった」ことしか言わない
2. **日足なので仲値アノマリーは原理的に扱えない**
3. **OHLCがない。** 1日1本の値だけ
4. スプレッドは1.0pip固定（日足では時間帯別に意味がない）

**採用判定の根拠には使わない。** レジームが変わったかの目安として見る。

### 期間別に見たUSD/JPYの性格

トレンド強度 = 全体の値幅 ÷ 日次変動の絶対値の総和。
1に近いほど一直線に動いたことを意味する。

| 期間 | 年数 | 始値→終値 | 年率ボラ | **トレンド強度** |
|---|---|---|---|---|
| 2000-01〜2012-01 | 12.0年 | 101.7 → 77.0 | 10.5% | 0.016 |
| 2012-01〜2022-03 | 10.1年 | 76.7 → 114.7 | 8.6% | 0.037 |
| **2022-03〜2026-08** | **4.4年** | **115.4 → 159.2** | 10.7% | **0.056** |

**直近ほどトレンドが強い。** 2022年以降は2000-2012年の3.5倍。
ボラティリティはほぼ変わらないのに一方向に動いている。

### ブレイクアウト（窓40日）を期間別に見る

| 期間 | ネットシャープ | PF | 総リターン | 取引回数 |
|---|---|---|---|---|
| 2000-01〜2012-01 | -0.18 | 0.78 | -24.46% | 50 |
| 2012-01〜2022-03 | +0.24 | 1.38 | +18.93% | 43 |
| **2022-03〜2026-08** | **+0.80** | **4.26** | **+42.33%** | **16** |

数字だけ見れば「2022年以降はトレンドフォローが効く」と言いたくなる。**言えない。**

| 理由 | 数字 |
|---|---|
| 取引回数が足りない | **16回**（基準は200以上） |
| 推定誤差が大きすぎる | シャープ +0.80 **± 0.55**（4.4年） |
| 信頼区間下限 | **+0.25**（足切り0.51を下回る） |
| 期間の切り方を後から決めている | 2022-03という境界も窓40日も、データを見てから選んだ |

最後の点がとくに重い。**期間を切って良い区間を探す行為そのものが選択バイアス**で、
[03 §3](03-検証プロトコル.md) が防ごうとしているものそのもの。
上の表は記述であって検定ではない。

### 全期間（2000-2026）での採用ライン判定

| # | 基準 | 結果 |
|---|---|---|
| 1 | 取引回数 200以上 | ○ 217 |
| 2 | シャープ下限 > 足切り(0.33) | **× -0.13** |
| 3 | PF 1.2以上 | **× 1.08** |
| 4 | 最良年を除いても正 | **× -7.46%** |
| 5 | スプレッド1.5倍でPF 1.0以上 | ○ 1.220 |
| 6 | パラメータ±20%で半減しない | **× -70%** |
| 7 | ブートストラップ5%点 > 0 | **× -0.26** |

**不合格。** とくに基準6が効いた。基準値（窓40日）のシャープ0.14に対し、
窓を32日にすると **-0.10**（比率 -70%）。少し動かすと符号が変わる。
[03 §8](03-検証プロトコル.md) の「パラメータを少し動かして崩れるなら偽物」に該当する。

### この節の結論

**2022年以降のトレンド性は実在する。しかしそれを取れることの証明にはなっていない。**

4.4年・16取引では何も確定できない。これは
[05 検証5](05-検証結果.md) で確認した「短期間ではシャープが測れない」問題の再現でもある。

## 8. 次の一手

Notionのメモにあるとおり「不合格でも失敗ではない」。
むしろ1本目であっさり合格したときのほうがバグを疑うべきだった。
ここまでで **検証基盤が信用できることと、最初の仮説が外れたことの両方**が分かった。

優先順位：

1. **2022〜2026年の «日中» データを揃える**（最優先）
   日次では埋まったが、日中は依然として2022年3月までしかない。
   このコンテナから到達できる範囲では見つからなかった。
   ローカルでHistDataから取るのが確実（[06 §5](06-Phase1実行記録.md)）。
   M5・bid/ask付きが取れれば、仲値も直近レジームも精密に判定できる
2. **次の仮説へ** — [03 §9](03-検証プロトコル.md) の手順で
   時間帯系・平均回帰・キャリーなど、仲値とは源泉の異なるものを試す
3. 束が2本以上になったら戦略間相関の判定を追加（基準7）

### レジストリの状態

```
  ID  戦略             段階  グリッド  シャープ  結果
   1  nakane           WF        1    -1.19   不合格
   2  breakout         WF        5     0.42   不合格
   3  breakout_slow    WF        5     0.07   不合格

累計試行回数: 11 本 → 10年データでのDSR足切り 0.51
```

試行を重ねるほど足切りが上がる（6本のとき0.41 → 11本で0.51）。
**思いつきで数を撃つと、あとから本物を見つけても通せなくなる。**

試行回数はレジストリに積み上がっていく。試すほど足切りが上がるので、
**思いつきで数を撃たない**こと。
