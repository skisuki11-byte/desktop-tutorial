# ともしび UI設計 — 判断と根拠

企画書 v2（Notion「ともしび — ペット供養アプリ 企画（v2 / 検証済み）」2026-09-13）を
画面に落とすにあたって下した判断と、その根拠を残す。

ここに書かれた「採らない」は、開発中に必ず揺らぐ。継続率が伸び悩んだとき、
採らないと決めたものは必ず「手軽な解決策」として候補に挙がる。そのときにこの文書を読む。

## 1. 分析した事例

### 失敗事例

**Facebook「Year in Review」（2014年12月）**
その年に亡くなった6歳の娘の写真を、紙吹雪のイラスト付きで「あなたの1年はこんな感じ！」と
ニュースフィード最上部に自動表示した。Web技術者 Eric Meyer 氏がこれを
*Inadvertent Algorithmic Cruelty*（意図せぬアルゴリズムの残酷さ）と書き、Facebook は謝罪した。

- 出典: https://meyerweb.com/eric/thoughts/2014/12/24/inadvertent-algorithmic-cruelty/
- 報道: https://www.forbes.com/sites/amitchowdhry/2014/12/29/facebook-year-in-review-apology/

**構造的な失敗理由**：大多数で正しく動くコードが、少数の喪失体験者に対してだけ最悪に振る舞う。
しかも「予告なし」と「祝祭的な装飾」が重なった。片方だけなら耐えられた可能性がある。

→ **本案への反映**
1. 再会ムービーを自動再生しない。必ず予告画面を挟む（画面09）
2. アプリ全体から紙吹雪・達成バッジ・称賛アニメーションを排除する
3. お参り完了後に出すのは一言だけにする（画面04）

**Replika（2023年2月の仕様変更）と、いわゆるグリーフボット全般**
常時対話できるAI人格は強い愛着を生み、提供側の都合で人格が変わると利用者が深く動揺する。

→ **本案への反映**：常時対話のAIチャットを実装しない。
手紙には常時「AIが書きました」を表示し、隠さない（画面08）。

**Duolingo型ストリーク（この文脈でのみ失敗）**
学習アプリでは継続率を大きく改善した実証済みの手法。だが弔いの文脈では、
1日休んだ人に「途切れました」と告げることは、故人への不義理を演出する行為になる。

→ **本案への反映**：連続お参り記録を実装しない。数字は常に「前にある節目」だけを示す。

### 成功事例

**Google フォト／Apple「メモリー」の除外設定**
両者とも、自動生成される思い出の提示に対して後年、除外の仕組みを追加した。
Google フォトは設定で「ユーザーとペットを非表示」と日付範囲の除外、
Apple は人物に対する「おすすめに表示しない」を持つ。

- 参考: https://www.androidpolice.com/how-to-hide-memories-of-certain-people-pets-and-dates-in-google-photos/
- 参考: https://tomsguide.com/phones/how-to-hide-someone-from-your-iphone-memories

**教訓**：自動提示は、除外できて初めて安全になる。しかも両者とも**後付け**だった。

→ ~~**本案への反映**：アルバムの全カードに「この期間は出さない」を常設し、設定の奥に隠さない。
章ごとに「出さない」を選べる（画面07）。~~

~~**ただし、既定では何も隠さない。**~~ 提案の段階では闘病期・最期の数週間を
既定で非表示にするつもりだったが、採らないことにした（追記2）。
のちに章ごとの除外そのものも全廃した（追記3）。

> **この教訓の当てはめを誤っていた。** Google／Apple で問題だったのは*不意打ち*、
> つまり本人が求めていないのに思い出が出てくることだった。
> ともしびのアルバムは本人が開きに行くもので、不意打ちの構造がない。
> 除外を借りてくる前提が、そもそも成り立っていなかった。詳しくは追記3。

**Stripe（配色とタイポグラフィの禁欲主義）**
信頼が要る製品ほど、色数と装飾を減らすほうが読みやすさと信頼感が上がる。

→ **本案への反映**：彩度のある色は灯りの橙1色のみ。
成功の緑・エラーの赤は通常の導線に登場させない（この製品に「間違い」はないため）。

**儀式効果（Norton & Gino, 2014）**
決まった手順の行為が喪失後の悲嘆を軽減する。宗教的意味がなくても、
本人が効くと信じていなくても効果が出た。効いているのは内容ではなく、
**自分でコントロールできる手順が毎回同じであること**。

→ **本案への反映**：お参りの4動作は順序・動き・音を固定。並べ替えも追加もできない。
**この画面に限り「飽きさせない工夫」は害**（画面03）。

**ピーク・エンドの法則（Kahneman）／予期効用（Loewenstein）**
体験の記憶は最も強い瞬間と終わり方で決まる。また人は良いことを待つ期間からも効用を得る。

→ **本案への反映**：再会ムービーの終端に「また来年、この日に。」を置く。
進捗バーは置かない（残り秒数を数えさせることが別れのカウントダウンになる）。

## 3. 実装しないUI

| 手法 | 継続率への効果 | それでも採らない理由 |
|---|---|---|
| 連続お参り記録（ストリーク） | 大 | 悲嘆に罪悪感を接続する |
| 達成バッジ・紙吹雪・称賛アニメ | 中 | 弔いが実績管理に変わる |
| ランダムに届く思い出 | 大 | 反復視聴を加速させる |
| 退会引き止めダイアログ | 中 | 手放せる自由がある人だけが安心して留まれる |
| 他人との比較・ランキング | 中 | 悲しみ方に優劣を持ち込む |
| 常時対話できるAIチャット | 大 | 最も依存を生み、最も失望される |

## 4. 既存アプリとの関係

このリポジトリの他アプリ（cashbook / dividend / yosou / solar / sekaishi / youtube）とは
**トークンの構成（変数名・余白スケール・角丸の考え方・ダークモードの持ち方）を共有し、値だけを差し替える**。

意図的に反転させたのは1点：**既定テーマをダークにした**。
理由は3つ。(1) 灯りは暗闇でしか灯りに見えない。(2) 悲嘆は夜に強まり、お参りは就寝前の習慣になる。
(3) 1画面の主役を灯り1つに絞るには、他をすべて沈める必要がある。

書体の使い分け（名前・日付・手紙は明朝、操作ラベルはゴシック）は、
cashbook が帳簿という主題に明朝を当てた前例と同じ考え方。

# 追記：作り直し（2026-09-14）

## 方向を変えた

夜の弔い → 昼の「いっしょにいる」。

前の案は「別れを受け入れる」側に寄っていた。**Continuing Bonds（継続する絆／
Klass, Silverman & Nickman, 1996）** は、故人との関係を続けることこそ健全だとする
現在の主流モデルで、「手放す」を前提にした古いグリーフ観を置き換えたもの。
利用者の「1年後のお楽しみではなく、もっと身近にここにいる感を」という直感は、
こちらに沿っている。

| | 前 | 今回 |
|---|---|---|
| 地 | 夜 #0e1013 | 昼 #FDFAF2 |
| 書体 | 明朝 | Zen Maru Gothic ＋ Zen Kaku Gothic New |
| 絵 | シルエット1体 | いぬ・ねこの手描き風イラスト（写真が入れば消える） |
| 再会 | 年に一度だけ | 端末の動画をいつでも |
| 数字 | 次の節目まであと◯日 | おまいり通算◯回目 |
| — | — | おまいりの庭（花＝通算） |

**捨てたもの**：年1回にすることで得ていた予期効用（待つ364日に意味を持たせる）と、
「年に一度しか渡さないものがあるからアンインストールできない」という解約防止。
日常的に会えるようにした以上、この2つは効かない。継続の理由は別に要る。

## 通算回数はストリークではない

利用者の「何回目、を入れて」に対して、**累計**で答えた。

| | 連続記録 | 通算回数 |
|---|---|---|
| 1日休むと | 途切れる | 何も起きない |
| 表示 | 「途切れました」 | 減らない |
| 生む感情 | 罪悪感 | 積み重なった実感 |

Duolingo で継続率を大きく上げた仕掛けが、弔いの文脈では凶器になる。
庭の花も同じ性質で、枯れない・減らない・他人と比べない。

## 写真が入らなかった原因（記録として残す）

1. **IndexedDB が使えない環境がある。** 埋め込み（iframe）表示、iOS Safari の
   サードパーティ制限。`indexedDB.open()` が通っても書き込みで落ちる環境もある。
2. **失敗を誰も受け取っていなかった。** `shrink().then().then()` に `.catch` が無く、
   保存が失敗すると「取り込んでいます…」のまま永久に止まった。

対策は、(a) 起動時に**実際に書いて消す**試験で可否を判定する、
(b) 保存関数は決して reject せず `{ok:false, reason}` を返す、
(c) reason を人の言葉にして**必ず画面に出す**、の3点。

**この製品では、黙って失敗することが最悪の挙動である。**
弔いの対象の写真が入らず、理由も出ないという体験は、機能の欠落より重い。

# 追記2：最期の数週間の写真を、既定で隠さないと決めた（2026-09-14）

利用者の判断で「非表示にしなくてよい」となった。**この判断のほうが正しいと考える。**

## なぜ隠そうと提案したのか

3つ重ねていた。

1. **Google フォト・Apple メモリーの教訓。** 自動で思い出を提示する機能は、
   除外の仕組みを後付けするまで人を傷つけた。除外できて初めて安全になる。
2. **闘病期の写真の性質。** 最期の数週間は、管につながれた姿や、痩せた姿や、
   病院での写真であることが多い。準備なく目に入りやすい種類の画像。
3. **ピーク・エンドの法則との整合。** 再会ムービーで「終わりに何を置くか」を
   設計した以上、アルバムでも最悪の画像が終端に来るのを避けたかった。

## なぜ取り下げるのが正しいか

1. **本人の写真で、本人の悲しみである。** 既定で隠すのは、自分のペットの
   どの姿を見てよいかをアプリが決める行為になる。差し出がましい。
2. **隠すこと自体が意味を持ってしまう。** 「この写真は見せられないほどひどい」
   という枠づけになる。多くの人にとって最期の数週間は、最後に抱けた時間でもある。
3. **Continuing Bonds と矛盾する。** 関係を続けることを中心に置き直したのに、
   つらい部分だけ編集して外すのは、その方向と逆を向いている。
4. **そもそも判定が雑。** 撮影日から「最期の数週間」を機械的に切ると、
   最後の旅行のような良い記憶まで一緒に隠れる。

## 残すもの

**章ごとの「この期間は出さない」は残す。** Google/Apple の教訓が言っているのは
「除外できること」であって「既定で隠すこと」ではない。
選べる状態にしておいて、選ぶかどうかは本人に委ねる。

> **追記3で撤回。** この「残すもの」も、のちに全廃した。理由は末尾の追記3。

## 記録の訂正

既定で隠す処理は、**実装には一度も入っていなかった**。提案書（`proposal.html`）に
書いただけで、アプリの `photoHidden` は空で始まり、本人が押したときだけ埋まる。
それにもかかわらず、PR本文や説明で「既定で非表示」と書いていた。
この追記は、提案を正式に取り下げると同時に、記録を実装と一致させるもの。

# 追記3：章ごとに隠す機能をやめ、アルバムを開けるようにした（2026-09-14）

利用者から2つ。**「アルバムが登録できるけど、見れない」**、
そして**「この期間は公開しないとあるが、全て公開にして良い」**。

## 見れなかったのは、こちらの手落ち

写真は入るし、章立ても出ていた。だが**章を開く手段がどこにもなかった**。
章の行には「···」のメニューしか押せるものがなく、その中身は
「この期間は出さない」と「名前をつける」だけ。
つまり**隠す操作は作ってあって、見る操作を作っていなかった**。

入れた写真が見られないアルバムは、アルバムではない。これは論点ですらなく、
ただの欠落である。章の行そのものを押せるようにし、写真の一覧と、
一枚ずつ大きく見る画面を足した。

## 隠す機能の全廃

追記2で「除外できることと既定で隠すことは別」と書き、章ごとの除外は残した。
今回それも外す。

理由は、**除外という機能が支払わせている代償のほうが大きい**と判断したため。

1. **隠す操作だけがあって、見る操作がなかった。** どちらを作りたかったのかが
   そのまま表れている。設計の重心が「見せない」側に寄っていた。
2. **除外の必要は、Google/Apple の文脈から借りてきたもの。** あちらは
   *不意打ち*が問題だった。突然「3年前の今日」として出てくるから傷つく。
   ともしびは利用者が**自分でアルバムを開きに行く**。不意打ちの構造がない。
3. **自分で入れた写真である。** カメラロールから1枚ずつ選んで入れたものを、
   あとで隠す前提で設計するのは筋が通らない。見たくなければ入れなければよく、
   入れたあとで要らなくなれば**消せばよい**（一枚ずつ消せるようにした）。

除外を外したぶん、**消す**を写真ごとに用意した。
隠す（見えないが残る）より、消す（無くなる）のほうが意思がはっきりする。

## 記録の訂正

追記2の「残すもの」節は、この追記で撤回された。
節そのものは消さずに残し、撤回された旨だけを付けてある。

# 追記4：享年・命日と、戒名を入れた（2026-09-14）

利用者から「トップに享年何歳・何月何日没を入れて」「戒名を入れて、登録するペット固有のものに」。
戒名の中身は任せる、とのことだったので、ここに設計の根拠を残す。

## 戒名を、アプリが作ってよいのか

作ってよいとは考えていない。**戒名はお寺が授けるもので、アプリが授戒できるはずがない。**
実際、動物に戒名を出すこと自体が宗派によって扱いが分かれる（戒＝戒律を保つ主体という前提があるため）。
一方で、ペット霊園や動物供養を行う寺院が、牧会的な配慮として戒名や法名を出す例は現に多い。

そこで**授けるふりをしない**ことを設計の起点にした。

1. 画面にもドキュメントにも「**このアプリがこの子のために選んだ名です。お寺が授けたものではありません**」と明記する
2. **書きかえられる**。お寺からいただいた戒名があれば、そちらが常に優先される
3. **出さないこともできる**。戒名になじみのない人に、宗教的な様式を既定で押しつけない
4. **どの字がどこから来たかを、すべて開いて見せる**。由来の分からない名を渡すのは贈りものではなく押しつけになる

4 が肝だと考えている。自動生成された文字列を「あなたの子の戒名です」と出すだけなら、
ありがたみを装った乱数でしかない。**根拠を全部見せて初めて、選んだ名だと言える。**

## 組み立て

人の戒名にならい、**道号2字＋法号2字＋位号2字**。

| 位置 | 何から決まるか | 例（モコ・犬・2013.4.10生・2025.11.3没） |
|---|---|---|
| 道号 | 旅立った季節（没月を2か月ずつ6つに） | **冬晴** 冬の晴れたころに旅立った |
| 法号・上 | この子の名の頭の一字 | **望** 「モコ」の頭の一字 |
| 法号・下 | 生まれた季節（なければ種類から） | **和** 春に生まれた |
| 位号 | ペット供養で広く使われる結び | **霊位** |

→ **冬晴望和霊位**

カタカナ・ひらがなの名は、頭の音を一字に置きかえる（モ→望、ハ→晴）。
これは**万葉仮名と同じ、音を借りるやり方**で、人の戒名でも名の一字を採るのが通例なのに倣っている。
漢字の名ならその一字をそのまま使う。

意図したのは、**生まれた季節と旅立った季節が名の両端に来る**こと。
名前がその子の一生をそのまま包む形になり、6字がこの子だけのものになる。
同じ名・同じ種類でも、生没の季節が違えば別の名になる。

## 表示

**縦書きの毛筆で、遺影の右に立てる。** 位牌と同じ構えにした（当初は写真の下に横書きで置いていたが、追記5で改めた）。
縦書きの日本語は右から左へ読むので、**右に置くのが順序として正しい**。

書体はこの一か所だけ毛筆にする。アプリの他の文字はすべて丸ゴシックと角ゴシックなので、
**書体と向きが変わること自体が「ここは格が違う」という合図**になる。

Stripe の禁欲主義（色数と装飾を減らすほど信頼感が上がる）と同じ考えで、
**色は増やさず、書体と向きの対比だけで格を作った**。

トップの並びは 戒名（右に縦）→ 名前 → 享年・命日 → 生年月日・いっしょにいた日数。
一番大きいのは**名前**のままにしてある。戒名は儀礼の名で、飼い主がこの子を呼ぶのは名前のほうだから。

### 縦に積むのに writing-mode を使わない

`writing-mode: vertical-rl` で組んだところ、**6字が同じ場所に重なった**。
毛筆体が届かず別の書体に落ちたとき、その書体に縦書きの字送り（vmtx）が入っていないと、
字送りが 0 になる。実測で 6 字の高さが 15px しかなかった（字間の指定ぶんだけ）。

**1字ずつ箱にして縦に並べる**ことで解決した。どの書体でも必ず縦に立つ。
毛筆が読み込めない・オフラインのときは明朝に落ちるが、**縦書きと墨色は残るので格は保たれる**。
書体の有無に見た目の根幹を預けない、というのがここでの判断。

字数に応じて大きさを自動で決め、遺影の絵（高さ212px）からはみ出さないようにしている。
院号つきの長い戒名を手で入れても収まる。

## 享年

満年齢で数える。1年に満たない子は「享年 6か月」と月で出す。
**0歳と出すより、6か月と出すほうがその子の時間に近い。**

# 追記8：じぶんの画面で「何を見るのか」を言い切った（2026-09-14）

利用者から4つ。「ここで何を見るのかをはっきりさせたい」「ペットの死を乗り越えて自分らしく

「答えなくても大丈夫です」は、押しつけを避けるつもりで書いた。
だが**この記録はこのアプリの要**である。要になるものに「やらなくていい」と添えるのは、
配慮ではなく**自信のなさ**だった。外した。

代わりに置いたのは「良し悪しはありません。いまの感じに近いものを。」
**やらなくていいとは言わず、間違いはないとだけ言う。** 押しつけずに勧めるのは、これで足りる。

見出しの下に置いた：**「あの子を見送ったあとの毎日を、あなたらしく生きていくための場所です」**

利用者の言葉は「乗り越えて」だったが、そこは変えた。

Continuing Bonds（Klass, Silverman & Nickman, 1996）の立場で、このアプリの前提でもある。
「乗り越える」と書くと、忘れることが目標のように読めてしまう。
**「見送ったあと」なら起きた事実だけを言う**ので、前提と矛盾しない。

> ここで見るのは、良くなったかどうかではありません。**波のかたち**です。

これは Dual Process Model をそのまま画面の言葉にしたもの。
**グラフが右肩上がりでないことは失敗ではない**と、見る前に言っておく。

## 記録の状態を、日のこととして言う

「記録しました」→**「きょうは 記録しました」**。
1日に1つの記録なので、いつのことか分かる形にした。

補助の行も状態で変える。
- まだ：良し悪しはありません。いまの感じに近いものを。
- 記録済：**押しなおせば、あとから変えられます。**

保存は `selfLog[日付] = 値` で、同じ日を押しなおせば**後から押したほうで上書きされる**。
できるのに言っていなかったので、書いた。

実測で確認：2 → 5 と押しなおすと、記録した日数は8のまま値だけが5に変わり、
開き直しても5が残り、おまいりのあとの画面にも同じ状態が出る。

# 追記11：ローマ字の名前と、戒名の注記（2026-09-14）

利用者から2つ。「戒名は他の名前でもちゃんと名前にあった形ででるの？」に答えて確かめたところ、
**ローマ字の名前だと戒名が空になる**不具合を見つけたので、確認とあわせて直した。
続けて「戒名のところに、ちゃんと戒名という表記もして。いきなりだとなんだかわからないから」。

## ローマ字の名前で戒名が出なかった

`headChar()` は、漢字ならそのまま・平仮名とカタカナは音の表から拾う、という2つの道しか
持っていなかった。**Coco・Momo のようなローマ字の名前は、どちらにも当てはまらず空文字を返す。**
戒名の6字のうち1字が決まらないので、`kaimyoParts()` が `null` を返し、**戒名そのものが出なくなる**。
エラーにはならず、静かに非表示になるだけなので、報告がなければ気づけなかった。

### 直しかた

ローマ字の綴りから頭の音を拾う対応表（`ROMA`）を足し、平仮名の道が外れたときだけ
最後の手段として通すようにした。長い綴りから先に照合する（"cho" が "c" に化けて
取りこぼさないように）。日本語の音韻にない区別は寄せる：
`l` は `r` に、語頭の `c`（`ch` を除く）は `k` の音として扱う（Coco→Koko）。

厳密な発音より、「先頭がどの行の音か」さえ合えばこの用途には十分と判断した。

| 名前 | 戒名 | 頭の字の由来 |
|---|---|---|
| Coco | 秋水**幸**和霊位 | Coco→Koko→こ→幸 |
| Momo | 薫風**望**清霊位 | Momo→も→望 |
| Charlie | 冬晴**千**和霊位 | Charlie→cha→千 |
| Cookie | 寒月**幸**実霊位 | Cookie→koo→こ→幸 |

既存の仮名・漢字の名前（モコ・太郎など）は出力が一字も変わらないことを確認した
（`headChar` の最初の2つの道は手を加えていない）。

## 「戒名」の注記

縦書きの毛筆だけを遺影の横に出しても、はじめて見た人には何の文字か伝わらない。
**「戒名」の2字を、毛筆の右肩に小さく添えた。**

注記は本文ではないので、書体をあえて分けた。毛筆ではなく地の角ゴシック、
色も墨より薄い `--muted`。本文の字を大きくしても注記までつられて大きくならないよう、
相対単位ではなく固定の10pxにしている。

設定画面には既に見出し「戒名」があるので、そちらには重ねて出さない
（`.kaimyo-box .kaimyo-label{display:none}`）。

注記の高さぶん、遺影の絵からはみ出さないための字の大きさ計算（`fitBrush`）にも
15px を追加で差し引いた。390×844・320×568・戒名6字〜12字・昼夜の組み合わせで
はみ出しがないことを実測した。

# 追記12：「てがみ／やめる」が見にくかった不具合を直す（2026-09-14）

利用者から実機の画面を見せてもらった。「てがみ」が「てが」「み」に割れて2行になり、
「やめる」との間が不自然に空いていた。続けて「やめるボタンにして」。

## 原因：CSSの詳細度の事故

前回の監査（追記9）でタップ領域を44pxに広げるため `.bar-btn` を足した。
このとき `.bar-btn{width:auto; min-height:44px; ...}` を `.btn` より**前**に書いてしまった。

`.bar-btn` も `.btn` も単一クラスのセレクタで詳細度は同じ（0,1,0）。
同じ詳細度がぶつかったとき、**あとに書かれたルールが勝つ**。`.btn` が後に来るので、
`.btn{width:100%; min-height:60px}` が `.bar-btn` の指定を丸ごと踏みつぶしていた。

# 追記14：iPhone・Android 横断チェック（2026-09-14）

利用者から「iPhone、Android両方で全て使いやすく動くように確認して」。
実機7サイズ（iPhone SE(1st)〜14 Pro Max／Galaxy S8系・Pixel 7・Galaxy Fold折りたたみ内）
×全11画面を自動測定し、見つかった実害のある不具合を直した。

## 見つけて直したもの

**1. 「ホーム画面に追加」の案内が iOS 前提のままだった。**
「共有ボタンから」は iOS Safari の場所で、Android のブラウザに共有ボタンの列はなく
右上の「⋮」メニューにある。存在しないボタンを探させていた。
`navigator.userAgent` で iOS／Android を見分け、機種ごとの文言を出し分ける
`homeHint()` を作り、3箇所（初回登録・おうち・設定）の案内文をこれで埋めるようにした。
iPadOS はデスクトップ名を名乗るため、`platform==='MacIntel' && maxTouchPoints>1` で
タッチ対応の Mac として個別に検出している。

**2. `color-scheme` を宣言していなかった。**
Android Chrome の「ウェブサイトを自動的に暗くする」は、`color-scheme` の宣言がない
ページをヒューリスティックに判定して勝手に反転させることがある。このアプリは
自前で昼／夜を切り替える設計なので、それとかち合うと意図しない配色になりうる。
iOS にはこの挙動がなく、この端末だけでは気づけない不具合だった。
`applyTheme()` で `document.documentElement.style.colorScheme` を
昼夜の切り替えと一緒に明示するようにした。

**3. 気分の5択ボタンが 320px 幅で 44px を割っていた。**
`.scale{gap:8px}` が幅を食い、iPhone SE(1st) で実測 40〜42px。
gap を 6px に詰めて 44.00px ちょうどまで確保した（`追記` 内既出、今回全端末で再確認）。

あわせて、「じぶん」画面と違い「おまいりのあと」画面（`.after`）だけ左右の余白が
26px（`.body` は20px）と6px広く、同じ `.selfask` カードを置くと5分割ボタンだけ
さらに2.4px/個縮んで iPhone SE(1st) で 42px に落ちていた（他画面は44px超で通っていたため
これまで見落としていた）。`.after .selfask` にだけ左右 `-6px` のマイナスマージンを足し、
外側の余白ぶんを打ち消して幅をそろえた。

**4. 設定のバックアップ行が 320px で2行に割れていた。**
「バックアップを書き出す」「バックアップから戻す」。すぐ上に見出し「バックアップ」が
あるので言葉の繰り返しは不要と判断し、「書き出す」「読み込む」に短縮した。

**5.（ついでに）タップの手ごたえが機種で揃っていなかった。**
Android は既定でボタンの形を無視した灰色の四角が光り、iOS の WebKit は既定でほとんど
何も光らない。どちらも半端で、しかも機種によって見え方が違う。
`-webkit-tap-highlight-color:transparent` で既定の光りかたを消し、
まだ専用の `:active` を持っていなかった要素（設定の行・戻る系ボタン・タブ・
お供え・選択肢群・章の一覧・季節の行・レター一覧など）に共通で `opacity:.6` の
押下フィードバックを足した。これは報告された不具合ではなく、横断チェック中に
気づいて直したもの。

## 判断して直さなかったもの

**Galaxy Fold の折りたたみ内側（280px幅）** は、気分の5択ボタンが上の gap 詰め後も
36px までしか確保できず（`280px - .body余白36px×2 - gap24px ÷ 5 = 36.8px`）、
「この端末のデータを消す」の行も2行に割れる。280px は現在のカード余白構造のままでは
5分割ボタンを44px×5に収める数式上の余地がない。これは折りたたみ機の**外側の
カバーディスプレイ**という一時的な確認用の表示面であり、このアプリを主に使う面ではない
と判断し、余白の構造自体を作り替えてまで追いかけるのは見送った。行の2行割れも、
タップ不能や表示欠けには至らず機能は保たれている。

## 確かめたこと

Playwright で iPhone SE(1st)〜14 Pro Max・Galaxy S8系・Pixel 7・Galaxy Fold の
7サイズ×全11画面を自動測定（横スクロール発生・要素の隠れによる欠け・見出しや
ボタンラベルの意図しない2行割れ・タップ領域44px未満、の4項目）。
自動測定が「44px未満」と拾った項目のうち、`.btn.bar-btn`（やめる／とじる、幅83×高さ44）は
実際には `min-height:44px` で固定されており、個別に高精度計測（設定の反映待ちを
長めに取って直接 `getBoundingClientRect()` を読む）すると常に高さ44.000pxちょうどで、
テスト側の計測タイミングによる誤検出と切り分けた（過去にも同種の誤検出を確認済み）。
実害のある4件（上記1〜4）を直し、5件目（タップ手ごたえ）は予防的に追加。
Galaxy Fold の折りたたみ内側の2件は上記の理由で既知の制約として残す。

# 追記18：遺影が丸い枠の中で縦に伸び、上下が切れていた（2026-09-14）

利用者から、実機の「おまいりのあと」画面のスクリーンショットとともに
「ここの写真が切れている」と報告。丸い遺影の上のほうに、写真ではない
一色の帯が見え、その下に顔の一部だけが写っている状態だった。

## 原因：構図の問題ではなく、grid の行の高さが解決できていなかった

最初は「顔が中央にない構図の写真を、そのまま中央で正方形に切り抜いたから」を疑ったが、
実際に計測すると違った。`.face`（遺影の丸い枠）は `display:grid;place-items:center`
で、中の `<img>` には `width:100%;height:100%` を指定してある。

ここに **CSS Grid の既知のはまりどころ**がある。行の高さを `grid-template-rows` で
明示していないグリッドでは、行は「中身に合わせて自動で決まる」。その中身（img）の
高さが「100%＝行の高さ」を指すのに、行の高さは中身（img）から決まる――という
循環になり、ブラウザは解決できずに `height:auto`（写真そのものの縦横比なりの高さ）
にフォールバックしていた。

実測すると、168×168の枠の中で img の実際のボックスは **158×474px**（横は正しいが、
縦だけ写真の縦横比なりに大きく伸びていた）。この縦に伸びた img が枠の中央にそろえられ、
はみ出た上下を `overflow:hidden` で切っていたため、`object-fit:cover` が本来行うはずの
「顔を中心に賢く切り抜く」が働かず、**単に写真の縦の中心にあるものが表示されていた**。
写真によっては、そこに顔ではなく背景が来てしまう。これが「一色の帯＋顔の一部」の正体。

`home-face`・`omairi-face`・`after-face`・`pick-face` はすべて同じ `.face` の
仕組みを使っているため、**遺影が表示されるすべての場所で同じように起きていた**はずで、
特定の1枚の写真や1画面だけの問題ではない。

## 直しかた

`.face img,.face video` に `position:absolute;inset:0` を足した。絶対配置にすることで
grid の行サイズ計算から外れ、`width/height:100%` は最も近い `position:relative` の
祖先（`.face` 自身、実寸168×168など）に対して直接解決されるようになる。
SVGの代役イラスト（`.face .art`）は絶対配置にしていないため、従来どおり
`place-items:center` で中央にそろう。

## 確かめたこと

無地の色や上下でグラデーションのある合成写真を実際に取り込み、Playwrightで
`<img>` の実測ボックスサイズが枠の実寸（例：168×168の枠なら158×158＝枠から
ボーダー4pxぶんを引いた内側）と一致することを確認した（修正前は158×474のように
縦だけ大きくずれていた）。home・omairi・after の3か所で同じ計測を行い、
すべて枠どおりに収まることを確認。全7端末×全11画面の自動測定でも、
既知の制約以外に退行がないことを確認した。

# 追記19：写真の位置・大きさを自分で合わせられるように（2026-09-14）

利用者から「最初に写真を選ぶ際に、枠の中に収まるようにサイズや左右上下を調整できる
ようにして」。追記18で切り抜きの不具合そのものは直したが、既定の中央そろえが
どの写真にも最適とは限らない。位置あわせをユーザー自身に委ねる機能を足した。

## 仕組み：object-position ではなく、自前でピクセル計算する

CSSの `object-fit:cover` と `object-position` を組み合わせれば近いことはできるが、
遺影は home（可変サイズ）・おまいり・おまいりのあと・写真えらび、の4か所で枠の
実寸がすべて違う（153〜168pxなど）。`transform:scale()` でズームを足すと
transform-origin と object-position の重なりが分かりにくくなり、場所ごとに
微妙にずれるおそれがあった。

そこで、写真の自然サイズ（`naturalWidth/Height`）と枠の実寸（`clientWidth/Height`）
を毎回測り、`width/height/left/top` を自前で計算して直接あてる方式にした
（`placeFaceImg()`）。位置は0〜1の分数（0＝写真の左端／上端が見える、
1＝右端／下端が見える）、大きさは1〜2.5倍（1＝枠にぴったり収まる最小倍率）で
`pet.faceX/faceY/faceZoom` に保存する。分数で持つことで、枠の実寸が違う4か所でも
同じ見え方になる。

## 操作

写真えらび画面（おむかえの3歩目、および設定「なまえ・写真・日づけ」から
同じ画面を再度開ける）で、丸い遺影を指でなぞると位置が動き、下のつまみで
大きさを変えられる。ドラッグ中は写真えらび画面の中だけをその場で動かし
（他の3か所を毎回作り直すと重い・ちらつく）、指を離した瞬間に保存して
home・おまいり・おまいりのあと にも同じ位置・大きさを反映する。

新しい写真に差し替えたときは、位置・大きさを既定（中央・そのまま）に戻す。
前の写真に合わせた位置は、新しい写真には意味がないため。

## 見つけて直した副作用：非表示の画面では幅が測れない

実装中、おまいり・おまいりのあと の遺影が新しい位置あわせに追従しないことに気づいた。
原因は、起動時に一度だけ位置を計算しているが、その時点でこの2画面は
`display:none`（まだ開いていない）で `clientWidth` が0のため、計算を
スキップしていたこと。`show()`（画面を切り替える関数）で、表示された
瞬間にもう一度計算しなおすようにして直した。

## 確かめたこと

Playwrightで、ズームつまみの入力に応じて写真の実寸（px）が数式どおりに変わること、
ドラッグの方向と量から計算される位置（faceX/Y）が数式どおりになること

を実測で確認）、離した後に home・おまいり・おまいりのあと の3か所すべてが

# 追記23：動画サムネイルの直しかたを、確実な方式に作り直す（2026-09-14）

追記22の直後、利用者から「まだ動画のサムネイルが表示されていないよ」。
実機（GitHub Pagesの反映待ちだった可能性が高い）で確認いただいたところ、
少し時間を置いたら表示されていたとのことだったが、調査の途中で
「シークして最初のコマを描かせる」という追記22の直しかた自体に、
確実性の面で弱いところがあると分かったため、より頑丈な方式に作り直した。

## 何が弱かったか

`<video preload="metadata">` を並べ、メタデータが読めた時点で
`currentTime` をわずかに動かして最初のコマを描かせる方式（追記22）は、
Playwright（Chromium）では狙いどおり動いた。しかし `preload="metadata"` は
仕様上「長さや寸法さえ分かればいい」という指定であり、**実際のコマの
データまで読み込む義務を持たない**。特にiOS Safariは、この状態から
`currentTime` を動かしただけでは実際のコマの取得・描画まで至らないことが
知られている。実機では効かない／時間差で効くことがある、確実性に欠ける
直しかただった。

## 新しい方式：1回だけコマを取り出し、静止画として持つ

動画を毎回タイルに直接並べてその場でコマを描かせるのをやめ、**動画の
最初のコマを1回だけ静止画（JPEG）として切り出し、`pet.videoThumbs[動画ID]`
に保存**するようにした。以後、タイルは普通の `<img>` として出す。
静止画は毎回同じように描かれるため、ブラウザやOSが動画をどこまで
読み込むかの違いに左右されない。

- 取り出すときは `loadeddata`（実際のコマのデータがそろった合図）を待ってから
  わずかにシークし、`seeked` を待って確定させる。取れなければ諦めて、
  その動画だけ従来どおり `<video>` をタイルに直接並べる（悪化はしない）。
- 新しく動画を追加したときも、すでにある動画（サムネイルをまだ持たない
  もの）も、画面を開いた瞬間に裏で自動的に作られる。利用者が何かする
  必要はない。
- 動画を消すときは、サムネイルもあわせて消す。

## 確かめたこと

MediaRecorderで作った検証用の動画（最初の約1秒だけ赤、その後青）を、
サムネイルを持たない「既存の動画」として保存した状態から「うごく」一覧を
開き、直後は従来どおり `<video>` のタイルであること、少し待つと自動的に
`<img>`（dataURL）に置き換わること、`pet.videoThumbs` に保存されること、
その画像が赤（最初のコマ）であることを確認した。全7端末×全11画面の
自動測定でも、既知の制約以外に退行がないことを確認した。
