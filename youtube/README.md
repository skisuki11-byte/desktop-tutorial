# チャンネル分析

自分の YouTube チャンネルを、**YouTube 公式のAPI**から直接読み取って分析するアプリ。
ブラウザだけで動きます。サーバーもインストールも不要です。

---

## まず結論：vidIQ には「つなげません」。でも、やりたいことはできます

| | vidIQ に接続 | このアプリ |
|---|---|---|
| 仕組み | **不可**。vidIQ は外部向けのAPIを公開していない | YouTube Data API v3 ＋ YouTube Analytics API（Google公式） |
| 自分のチャンネルの成績 | 見られる（有料） | **見られる。しかも同じ出どころ** |
| 視聴維持率・流入経路・検索語 | 見られる | **見られる** |
| 他人のチャンネルの維持率・流入 | 見られない | 見られない（YouTube が誰にも出していないため） |
| キーワードの検索ボリューム | 独自の**推定値**を出す | 出さない（推定を事実のように見せないため） |
| 費用 | 月額 | 無料（APIの無料枠のみ） |

vidIQ が自分のチャンネルについて見せている数字は、ほとんどが
YouTube Analytics API から取ったものです。つまり**出どころは同じ**で、
このアプリは同じ蛇口から直接汲んでいます。

vidIQ の拡張機能が叩いている非公開のエンドポイントを、ログイン中のCookieごと
真似れば技術的には繋がりますが、利用規約に反するうえ先方の都合でいつでも壊れるので、
この実装ではやっていません。

vidIQ にしかないのは「他人のチャンネルの推定値」と「キーワードの推定検索数」です。
どちらも**推定**であり、YouTube が公開している値ではありません。

## 準備（初回だけ。5〜10分）

Google に「自分用の窓口」を1つ作ります。無料です。

### 1. プロジェクトを作る

[Google Cloud Console](https://console.cloud.google.com/) を開き、
画面上部のプロジェクト選択 →「新しいプロジェクト」。名前は何でも構いません。

### 2. APIを2つ有効にする

「APIとサービス」→「ライブラリ」で、次の2つを検索して**有効にする**を押します。

- **YouTube Data API v3** … 動画の題名・説明文・タグを読むため
- **YouTube Analytics API** … 成績（視聴・維持率・流入）を読むため

> どちらか片方だけだと、画面の一部が「APIが有効になっていません」で止まります。

### 3. OAuth 同意画面を作る

「APIとサービス」→「OAuth同意画面」

| 項目 | 入れる値 |
|---|---|
| User Type | **外部** |
| アプリ名 | 何でも（例：チャンネル分析） |
| ユーザーサポートメール／連絡先 | 自分のメールアドレス |
| スコープ | ここでは追加しなくて構いません |
| **テストユーザー** | **自分の Google アカウントを追加**（これを忘れると弾かれます） |

公開ステータスは「テスト」のままで大丈夫です。自分ひとりで使う分には審査は要りません。

### 4. クライアントIDを作る

「APIとサービス」→「認証情報」→「認証情報を作成」→「**OAuth クライアント ID**」

| 項目 | 入れる値 |
|---|---|
| アプリケーションの種類 | **ウェブ アプリケーション** |
| 承認済みの JavaScript 生成元 | このページを置いている場所。例：`https://ユーザー名.github.io`<br>手元で試すなら `http://localhost:8000` も追加 |
| 承認済みのリダイレクトURI | **空のままでOK**（この方式では使いません） |

作成すると `000000000000-xxxxxxxx.apps.googleusercontent.com` という値が出ます。

> **生成元はドメインまで。** `https://ユーザー名.github.io/youtube/` のように
> パスまで入れると弾かれます。`https://ユーザー名.github.io` だけを入れてください。

### 5. クライアントIDを登録する

**方法A：端末に保存（手軽。1台だけで使うなら十分）**

アプリを開き →「設定」→ クライアントIDを貼って「保存」。

**方法B：`config.js` に書く（毎回の入力が要らなくなる）**

リポジトリの `youtube/config.js` を開いて、1行だけ書き換えます。

```js
window.YTLAB_CONFIG = {
  clientId: '000000000000-xxxxxxxx.apps.googleusercontent.com'   // ← ここ
};
```

こうすると**どの端末・どのブラウザで開いても入力が不要**になります。
スマホのアプリ内ブラウザ（LINEやXの中で開いたとき）やプライベートモードは
保存領域を残さないことがあり、方法Aだと毎回入力になってしまうためです。

> **公開リポジトリに書いて大丈夫？** 大丈夫です。
> ブラウザで動くGoogleログインでは、クライアントIDは**元々公開される値**です。
> このアプリを開いた人は誰でも通信を見れば読めますし、Google もそれを前提にしています。
> 守りは「値を隠すこと」ではなく、手順4で登録した**JavaScript生成元**（登録したドメイン以外では使えない）と
> **テストユーザー**（登録した人しか通らない）で掛かっています。
> 他人がこのIDを見ても、その人のブラウザで**あなたのチャンネルの数字は見えません**
> （見えるのはその人自身のチャンネルだけです）。
> 秘密にすべきなのは**クライアントシークレット**のほうですが、この方式では使わないので持つ必要がありません。

登録できたら「概要」に戻って「YouTube アカウントにつなぐ」。

**2回目からは押す必要はありません。** 一度許可すると、Google から下りた通行証を
期限（約1時間）まで端末に置いておき、期限内に開き直したときは
**Google に一度も問い合わせずそのまま読めます**。

> はじめは「前に通った」という事実だけを覚えて、開くたびに Google へ黙って
> 取り直しに行く作りにしていました。ところがこの取り直しは、スマホのブラウザ
> （とくにアプリ内ブラウザや、追跡防止が強い設定）ではしばしば拒まれます。
> 結果として毎回ログインになっていたため、通行証そのものを持つ方式に変えました。

置いてあるものについて：

- このサイト専用の領域に入るので、**他のサイトからは読めません**
- 権限は**読み取り専用**の2つ（収益を見たなら3つ）だけ。これを持っていても
  動画の投稿・変更・削除はできません
- **約1時間で自動的に切れます。** 切れたら捨てて取り直します
- 気になる場合は「設定」→「ログイン状態」で切れます。切ると以前と同じ動きに戻ります
- 「接続を解除する」を押すとすぐ消えます

途中で「このアプリは Google で確認されていません」と出ますが、
**自分が作った自分用のアプリ**なので「詳細」→「（アプリ名）に移動」で進んで構いません。
テストユーザーに自分を入れていれば通ります。

## 何が見られるか

| 画面 | 中身 |
|---|---|
| **概要（上段）** | **いまどういう状態か**の判定と、**次にやること**（最大3つ）。28日と90日を、視聴回数と**登録への転換**の両方で突き合わせて自動で出します |
| **分析の観点** | 判定の根拠。転換・平均視聴時間の裏取り・上位と長い尾の差・条件の揃った2本の差、そして**問題ではないと確認できたこと** |

| **動画** | 1本ごとの成績。並べ替え8種類（平均視聴率順、公開後の勢い順、点検の点数順 など） |

| **流入** | 流入経路の内訳、**YouTube検索で実際に使われた語**、外部サイト、再生された場所 |
| **視聴者** | 国・デバイス・登録者／非登録者・年齢と性別 |
| **収益** | 推定収益・広告収益・Premium からの収益・RPM・CPM・動画別の収益（**押すとその1本の詳細**：推定収益・RPM・維持率・流入） |
| **診断** | 題名・説明文・タグの点検、投稿間隔のばらつき、公開曜日ごとの成績 |

## 上部の登録者数について

つないだあと、上部にチャンネル名と登録者数が出ます。
**つないだ時点の値をそのまま出し、自動では取り直しません**（取り直したいときは「↻」）。

**「1人単位のリアルタイム」にはできません。**
YouTube は2019年から、APIで返す登録者数を**上位3桁に丸めて**います。
12,437人なら `12,400` と返ります。これは所有者が自分のチャンネルを見ても同じで、
正確な数は YouTube Studio でしか見られません。
Social Blade などの「リアルタイム登録者数」も、同じ丸めた値を何度も取り直している
だけなので、1人単位では動きません。
**動かない数字を何分おきに取り直しても、通信と1日の利用枠を使うだけ**なので、
このアプリでは自動の取り直しをしていません。

そのため、丸めた値の右に**直近28日の純増**を並べています。
こちら（`subscribersGained` − `subscribersLost`）は**丸められていない正確な値**です。

### どの動画で増えた／減ったか

「動画」タブの一覧と、概要の「この期間に伸びた動画」には、**増えた数と減った数を両方**添えています
（例：`登録＋2,903（−120）`）。増えた数だけ見せると、同時にどれだけ減っているかが分からず、
差し引きの実感が湧かないためです。

さらに、概要の「登録者の増減」カードを押すと、**動画ごとの内訳の上位5本**が見られます。

- **登録のきっかけになった動画** … 登録者が増えたときに直前に見ていた動画の上位5本
- **登録を解除された動画** … 登録を解除される直前に見ていた動画の上位5本

どちらの一覧にも、その動画の**逆方向の数字**（増えた動画なら減った数、減った動画なら増えた数）と
**解除率**を小さく添えています。緑＝増えた、赤＝減った、で色分けしていますが、符号（＋／−）も
必ず付けているので色が区別できなくても読み取れます。

**解除率は「視聴1回あたり何人が解除したか」**（解除数 ÷ 視聴回数）です。
実数だけでは再生数の違う動画を比べられないため（10万回で185人の解除と、
1千回で185人の解除では意味がまるで違う）、率も並べています。
0.0X% の桁で効く数字なので、1%未満のときだけ小数を増やして表示します。

**「その動画が原因で解除された」という意味ではありません。**
YouTube はここを「解除する直前に見ていた動画」として記録しているだけです。
たまたま最後に見ていた動画が記録されるだけなので、その動画の内容そのものが
理由とは限りません。傾向として繰り返し同じ動画が出てくる場合の手がかり、
くらいに捉えてください。

**解除数は、動画一覧の本体とは別の問い合わせで取っています。**
`dimensions=video` に `subscribersLost` を組み合わせた問い合わせを受け付けない
アカウント・期間があり得るため、視聴回数などを取る本体の問い合わせとはあえて分けています。
こうしておけば、こちらだけが失敗しても本体（視聴回数・総再生時間・登録のきっかけになった動画など）は
影響を受けません。失敗した場合は「登録を解除された動画」の枠だけ、黙って隠さず理由を出します。

## 数字の定義（どう計算しているか）

「なんとなく出ている数字」にしないため、集計方法をすべて書きます。

| 画面の言葉 | 元にしている値 | 計算 |
|---|---|---|
| 視聴回数 | `views` | 期間内の合計 |
| 総再生時間 | `estimatedMinutesWatched` | 期間内の合計（分→時間に変換） |
| 平均視聴時間 | `averageViewDuration` | **視聴回数で重み付けした平均** = Σ(平均視聴時間×視聴回数) ÷ Σ視聴回数 |
| 平均視聴率 | `averageViewPercentage` | 同じく視聴回数で重み付け |
| 登録者の増減 | `subscribersGained` − `subscribersLost` | 期間内の純増 |
| **登録への転換** | `subscribersGained` ÷ `views` × 1000 | 1,000回再生されるうち何人が登録したか。**解除は引きません** |
| 公開後1日あたり | `statistics.viewCount` ÷ 公開からの日数 | 累計の再生回数を経過日数で割ったもの |
| 推定RPM | `estimatedRevenue` ÷ `views` × 1000 | **合計どうしで割る** |
| CPM | `grossRevenue` ÷ `adImpressions` × 1000 | **合計どうしで割る** |
| 再生ベースCPM | `grossRevenue` ÷ `monetizedPlaybacks` × 1000 | **合計どうしで割る** |
| 収益化された再生 | `monetizedPlaybacks` ÷ `views` | 期間内の割合 |

**日ごとの平均を平均しない。** RPM や平均視聴時間を「日ごとの値の単純平均」で出すと
*平均の平均*になり、視聴が多い日と少ない日が同じ重みになってしまいます。
ここでは必ず合計どうしを割っています。YouTube 自身の定義と同じです。

**直近3日は入れません。** 分析値は確定まで2〜3日かかります。
入れると、あとから増えたぶんが「減った」ように見えてしまいます。

**増減率を出さない場合があります。** 比べる相手が0以下のときです。
−10人から＋10人を「200%増」と書くのは嘘になるためで、そのときは「—」と出ます。

**「登録への転換」で解除を引かない理由。** この数字が答えようとしているのは
「見た人が登録したか」です。解除を混ぜると「結局どれだけ残ったか」という
別の問いの答えになってしまい、作りが効いているかの判断に使えなくなります。
残った人数が知りたいときは、カードを押した先に「解除も引いた場合」を出しています。

## 「いまどういう状態か」の判定について

概要の上段は、**28日と90日を必ず両方**、そして
**視聴回数と「登録への転換」を必ず両方**見て判定します。

期間を2つ見るのは、片方だけでは読み違えるためです。

- 28日だけ … 1本当たった／外れただけで景色が変わる
- 90日だけ … 先月から起きている変化に気づけない

### なぜ視聴回数だけで判定しないのか

**これは、このアプリが実際にやってしまった見落としです。**

あるチャンネルで、28日も90日も視聴回数は増えていました。
判定は「伸びている（順調）」。ところが同じ期間に、
1,000回再生されるうちの登録者数は 7.64人 → 3.94人 と半分に落ちていました。
当たった1本を除くと 2.64人（−65%）。

視聴回数は「どれだけ届いたか」しか表しません。
届く数が増えれば、作りが悪くなっていても視聴回数は伸びます。
そのとき起きているのは「見られる数は増えたが、チャンネルとして残るものは減っている」
という状態で、伸びが止まった瞬間に数字に出ます。

そこで判定は、まず視聴回数の向きで土台を決め、
そこに「登録への転換」の増減を重ねて最終判定にしています。

| 直近28日 | 直近90日 | 土台の判定 | 意味 |
|---|---|---|---|
| ↑ | ↑ | 伸びている | 当たっている。本数を増やすのが効く |
| ↑ | ↓ | 持ち直している | 何かが効き始めた。直近の型を繰り返す |
| ↓ | ↑ | **勢いが落ちている** | いちばん注意すべき局面。ここで手を打たないと下降に入る |
| ↓ | ↓ | 下降が続いている | 本数より先に、1本ずつ原因を確かめる段階 |
| → | → | 横ばい | 続けても変わらない。何か1つ変えて反応を見る |

そのうえで、転換の増減が判定を書き換えます。

| 土台 | 登録への転換 | 最終判定 |
|---|---|---|
| 伸びている／持ち直している | **−25%以上** | **見られているが、登録に繋がっていない**（注意に格下げ） |
| 伸びている／持ち直している | −12〜−25% | 判定は変えず、一言に「転換は◯%落ちています」を添える |
| 落ちている | **＋12%以上** | 判定は変えず、「見に来た人が登録する割合は上がっている」を添える |

±5%以内は「横ばい」として扱います（日々の揺れの範囲のため）。
転換は28日と90日のうち、**落ち方の大きいほう**を使います。
28日だけだと1本の当たりで隠れ、90日だけだと気づくのが遅れるためです。

## 分析の観点（判定と「次にやること」のあいだ）

判定は結論の1行、「次にやること」は動きの指示です。
そのあいだに「なぜそう言えるのか」を置く場所が無いと、
出された打ち手を信じるしかなくなり、自分で判断できなくなります。

概要の「分析の観点」を開くと、次の5つが出ます。

| 観点 | 何を見ているか | 出るとき |
|---|---|---|
| **転換** | 1,000視聴あたり何人が登録したか（概要のカード・判定の表とも先頭） | 常に |
| **平均視聴時間の裏取り** | `averageViewDuration` と 総再生時間÷視聴回数 の食い違い | 常に |
| **上位と長い尾の差** | 上位5本とそれ以外で、登録の効率を比べる | 動画が6本以上あるとき |
| **条件の揃った2本の差** | 視聴も見られ方もほぼ同じなのに登録だけ2倍以上違う2本 | 見つかったとき |
| **問題ではないと確認できたこと** | 手を入れなくていいところ | 常に |

### 平均視聴時間の裏取り

平均視聴時間は2通りに測れます。

- `averageViewDuration` を視聴回数で重み付けした値
- 総再生時間（分）× 60 ÷ 視聴回数

**この2つが逆方向に動いていたら、平均視聴時間を根拠に判断してはいけません。**
ショート動画や長時間のライブが期間の途中から混ざると、
片方は本数の重み、もう片方は時間の重みで平均を取るため、向きが割れます。
このときチャンネル全体の平均視聴時間は「別のものを測っている」状態です。

実際に、API の平均視聴時間が 11分19秒 → 12分39秒 と伸びているのに、
総再生時間÷視聴回数では 10.3分 → 9.2分 と縮んでいた例があります。

### 上位と長い尾の差

視聴回数の大半は上位数本が作りますが、**登録は必ずしも同じ比率になりません**。
上位5本が視聴の59%・登録の84%を作っていた例では、
それ以外の動画は登録効率が3.6分の1でした。

このとき打つ手は「もっと伸ばす」ではなく「尾を直す」です。
上位5本の説明文・終了画面・固定コメントを、それ以外の動画に複製するだけで済みます。
公開済みの動画でも後から直せます。

### 条件の揃った2本の差

視聴回数も1回あたりの見られ方もほぼ同じなのに、登録数だけ大きく違う2本を探します。
**条件が揃っているので、差は中身の良し悪しではありません。**
残るのは「登録する理由が伝わったかどうか」だけで、原因が1か所に絞り込めます。

判定の条件は、視聴回数の比が1.4倍以内・平均視聴時間の比が1.25倍以内で、
1,000視聴あたりの登録が2倍以上違うこと。

### 問題ではないと確認できたこと

どこを触らなくていいかが決まらないと、目につく数字
（たとえば登録解除）に時間を使ってしまい、効く場所に手が回りません。
解除率が1,000視聴あたり1人を下回っていれば「解除は問題ではない」と明記します。

### 「次にやること」の優先順

打ち手は**最大3つ**しか出しません。多いと結局どれもやらないためです。
順番は土台から。投稿が止まっていれば、題名の話は後回しになります。

1. **投稿が止まっている** … 何を直しても、出さなければ始まらない
2. **平均視聴時間の低下** … 維持率は推薦の土台。ここが崩れると他が効かない
3. **登録への転換の低下** … 見られ方は保てていても、増えなくなる
4. **条件の揃った2本の差** … 原因が1か所に絞れている、いちばん動ける手
5. **新規に届いていない** … 登録者だけが見ている状態は、伸びが頭打ちになる
6. **検索から入られていない** … 題名・説明文で拾える入口を作れていない
7. **登録に進まれていない** … 新規には届いているが、次に繋がっていない
8. **長い尾が登録に繋がっていない** … 上位と同じ形に揃えるだけで効く
9. **当たった型をなぞる** … いちばん伸びた動画の作りを次に使う
10. **作りの点検** … 直せば効くと分かっている取りこぼし

どの項目も、判定に使った**実際の数字**を必ず添えます。
「サムネを改善しましょう」のような一般論は、どの数字を見て言っているのか
分からないので動けません。ここでは出しません。

## 数字の読み方（ここがいちばん大事）

数字を並べても伸びません。**どの数字を、どういう順で見るか**が決まっていないと動けません。

### 見る順番

1. **視聴維持率**（動画の詳細）… ここが全部の土台です。
   最後まで見られない動画は、どれだけ題名を直しても YouTube が広げてくれません。
   特に**冒頭30秒**。ここで半分を切っていたら、他を触る前にここを直します。
2. **流入経路**（流入）… どこから来ているか。
   - 「関連動画からのおすすめ」が主 → 中身は当たっています。本数を増やす段階。
   - 「YouTube検索」が主 → 検索語が効いています。同じ語で次を作る。
   - 「登録フィード・ホーム」ばかり → 既存の視聴者しか見ていない。新規に届いていない。
3. **YouTube検索で使われた語**（流入）… 推定ではなく**実際に使われた語**です。
   ここに出た語を次の動画の題名に使うのが、いちばん外れにくいやり方です。
4. **平均視聴時間**（概要）… 「％」より「分」を見ます。理由は次の項。
5. **登録への転換**（概要のカード）… 1,000視聴あたりの登録者数。
   ここが落ちていれば、視聴回数が伸びていても増え方は落ちます。
   押すと「登録に繋がっている動画」と「繋がっていない動画」が出るので、
   同じくらい見られている2本を見比べて、説明文の1行目・終了画面の違いを探します。

### よくある読み違い

- **平均視聴率（％）を動画どうしで比べる**
  20分の動画の30%（6分）と、3分の動画の60%（1.8分）では、YouTube が評価するのは前者です。
  長さの違う動画を並べるときは**％ではなく分**で比べてください。
  長尺のBGM・作業用動画では％はどうしても低く出ます。低いこと自体は問題ではありません。
- **公開直後の数字で判断する**
  集計は確定までに2〜3日かかります。このアプリが直近3日を含めないのはそのためです。
- **登録者数を主な目標にする**
  登録者は結果であって原因ではありません。動くのは維持率と流入のほうです。
- **視聴回数が増えていれば順調だと考える**
  視聴回数は「どれだけ届いたか」しか表しません。
  届く数が増えれば、作りが悪くなっていても視聴回数は伸びます。
  **1,000視聴あたりの登録者数**と一緒に見てください。こちらが落ちていれば、
  本数を増やしても同じ比率でしか積み上がりません。
- **本数を増やせば伸びると考える**
  伸びなかった動画を量産しても、伸びない理由がそのままコピーされるだけです。
  1本を直してから次に行くほうが早い。

### 診断の点数について

「診断」タブの点数は**vidIQ の SEO スコアではありません**。
あちらの計算式は公開されていないので、真似ることはできません。

代わりに、YouTube 自身が公開しているクリエイター向けの案内と、
**直せば効くと分かっている作り方**のうち、APIで取れる情報だけで白黒つけられるものを
並べています。判定の根拠は各項目にそのまま書いてあります。

主な減点の理由：

| 症状 | なぜまずいか |
|---|---|
| 題名が長すぎる（半角換算60超） | 検索結果と関連動画で後半が「…」に切られ、読まれない |
| 説明文の冒頭が定型のあいさつ | 折りたたみ前に出るのは最初の2〜3行だけ。そこが空振りになる |
| 説明文が全動画で使い回し | 動画ごとの違いが伝わらない |
| ハッシュタグが15個超 | YouTube 側で**全部無効**になる（付けていないのと同じ） |
| タグが30個超 | 効果がないうえ、関係の薄い語は「誤解を招くメタデータ」に当たりうる |
| 5分超なのに章（チャプター）がない | 離脱しかけた人が別の場所に飛ぶ道がない |
| 章はあるが 00:00 から始まっていない | 章として認識されない |

## 収益について

「収益」タブで、推定収益・広告収益・YouTube Premium からの収益・RPM・CPM を表示します。

**もう一度だけ同意が必要です。** お金の情報は別の権限
（`yt-analytics-monetary.readonly`）になっているためです。
最初からまとめて求めると、収益化していないチャンネルにも要らない同意を強いることになるので、
「収益データを読み込む」を押したときだけ求める作りにしています。こちらも読み取り専用です。

読むときの注意：

- **これは推定値です。** YouTube 側の月末調整（無効なトラフィックの除外など）で増減します。
  確定額は AdSense の支払いレポートで確認してください。
- **推定収益は「手取り」、CPM は「総収入」基準です。** 推定収益は YouTube の取り分を引いたあと、
  CPM の計算に使う総収入は引く前。並べると必ず CPM のほうが大きく見えますが、異常ではありません。
- **RPM のほうが CPM より大事です。** CPM は広告単価の話ですが、
  RPM は「視聴1000回でいくら手元に残ったか」。動画の作り方で動くのは RPM のほうです。
- YouTube パートナープログラムに参加していないチャンネルには収益の記録自体がないので、
  その旨を表示して終わります。

### 動画別の推定収益を押すと

棒を押すと、その1本の詳細が開きます。金額だけでなく **推定RPM** を並べ、
チャンネル全体の RPM より高いか低いかを添えています。

**金額の大小は、ほとんど再生数の大小で決まります。** 「どの動画が儲かる作りか」は
金額では分かりません。RPM を見てください。全体より RPM が高ければ、その長さ・その題材は
単価が取れているので、同じ型で増やすのが効きます。低ければ、動画が短くて広告の入る場所が
少ないか、広告主が付きにくい題材の可能性があります。

収益の数字は「収益」タブで取ったものをそのまま使うので、押しても追加の問い合わせはしません
（収益は権限も1日の枠も別なので、同じ数字を2度取りに行きません）。
そのため、詳細に収益が出るのは**収益タブから押したとき**だけです。

## 分析レポート（A4・1枚のPDF）

概要の下にある「**PDFで保存（印刷）**」を押すと、いま画面に出ている内容を
A4・1枚にまとめて、端末の印刷画面を開きます。そこで「PDFに保存」を選びます。

### 版面

上から順に、**題字帯 → 判定帯 → 数字の帯 → 2段組 → 動画表 → 流入 → 出典**。

いちばん嵩む「主な数字」を縦の表から**横の帯**に変えてあります。
5つの数字が1本の帯に収まり、読む側も縦に目を往復せずに済みます。

2段組は、左が「次にやること」、右が「分析の観点」と「問題ではないと確認できたこと」。
左を広く取っているのは、紙を見ながら動くのはそちらだからです。
右は根拠なので、**見出しと数字だけ**にしています
（理由の文章は画面で開けます。紙は触れないので、載せても確かめる先がありません）。

色を使うのは3か所だけです。判定の重さ（左の縦罫）、増えた／減った（符号と一緒に。
色だけには頼りません）、転換の枠（判定を書き換える数字なので1つだけ地を敷く）。
全面に色を敷かないのは、インクを使ううえ、どこが大事か分からなくなるためです。

### 載せていないもの

**グラフ。** 画面のグラフは触って値を読むためのもので、
紙に落とすと軸の数字が小さくなり、かえって読めません。

**「登録を解除された動画」の表。** この一覧は YouTube が
「解除する直前に見ていた動画」を記録したもので、その動画が原因という意味ではありません。
紙の上では注意書きごと読み飛ばされて「この動画が悪い」と誤読されやすく、
しかも打ち手に繋がりません。Claude に渡す文章のほうには入れてあります
（読む側が前提を汲めるため）。

### 1枚に収まる仕組み

版面は1枚に収まる作りですが、**中身の量は月によって変わります。**
観点が4つ出る月、題名の長い動画が並ぶ月、打ち手の説明が長い月——
決め打ちの文字サイズで組むかぎり、どこかで必ず溢れます。

そこで、印刷の直前に**紙と同じ幅で一度並べて高さを測り**、
溢れていれば根の文字サイズだけを縮めます。
他の寸法はすべてその相対（em）で書いてあるので、
字も余白も一緒に縮み、組みは崩れません。

縮める下限は 0.78 倍です。これ以上小さくすると紙の上で読めなくなるので、
そこまで縮めても収まらない場合は2枚目に送ります。
**読めない1枚より、読める2枚のほうがましだからです。**

> 以前このレポートが2枚になっていたのは、確認に使っていた作り物のデータが
> 軽すぎたためです（動画5本・短い題名・観点3つ）。
> いまは実際のチャンネルに近い重さ（長い日本語の題名、観点4つ、除外5件）でも
> 1枚に収まることを毎回確かめています。

> **なぜ「印刷」なのか。** PDFを作る道は3つあります。(1) 外部のPDFライブラリを読み込む —
> 日本語フォントを丸ごと抱える必要があり、ファイルが数MBになります。(2) サーバーで作る —
> サーバーが要ります。(3) ブラウザの印刷機能 — 追加のファイルも通信もゼロで、日本語も
> 端末のフォントでそのまま出ます。このアプリは「置くだけで動く」作りを崩したくないので (3) です。

## Claude に渡して分析してもらう

隣の「**Claudeに貼る用にコピー**」を押すと、この期間の数字を整えた文章が
クリップボードに入ります。Claude に貼り付ければ、そのまま相談できます。
数字の表だけでなく、「何を答えてほしいか」と「前提・注意点」まで入れてあります
（数字だけ渡されても、読む側は何を判断すればいいか分かりません）。

**アプリ側が付けた当たり（分析の観点）も一緒に渡します。** 伏せて数字だけ渡すと、
読む側は同じ道をもう一度たどることになり、そのぶん深いところまで進めません。
「この見立ては合っているか、他に何が読めるか」を聞く形にしてあります。
渡す文章には、登録への転換が**低い動画と高い動画の一覧**（同じ再生数の条件で切り出したもの）も
入れてあるので、条件を揃えた比較をそのまま任せられます。

**ボタンから自動でClaudeのAPIを呼ぶ形にはしていません。** ブラウザだけで動く
公開ページからAPIを呼ぶには、APIキーをページに埋め込むことになります。
公開リポジトリに置く以上、それは誰にでも読める状態を意味します
（クライアントIDと違い、APIキーは**本当に秘密にすべき値**で、
漏れればそのまま他人に使われ、こちらに課金されます）。
サーバーを1つ立てて、そこにキーを置いて中継させれば安全に実現できますが、
このアプリの「置くだけで動く」作りを崩すことになるため採っていません。
貼り付け1回で同じことができるので、実用上の差もほとんどありません。

## 順位（Social Blade など）について

**世界ランク・国別ランク・カテゴリ別ランクを、この画面に出すことはできません。**

- Social Blade は無料の公開APIを出していません（順位を取るには有料の Business API が必要）
- サイトの中身をブラウザから直接読むことも、向こう側の設定（CORS）で塞がれています

サーバーを1つ用意すれば回避できますが、このアプリは**置くだけで動く**作りにしてあるので、
そこは崩していません。概要の「チャンネルの規模」にワンタップで本家を開くボタンを置いてあります。

なお、そこに並ぶ**登録者数・総再生回数・動画数は Social Blade の推定値ではなく
YouTube 公式の値**です。順位以外の数字については、本家より正確です。

## 安全について

- 通信は**ブラウザから Google へ直通**です。当方のサーバーは一切経由しません。
- 要求する権限は**読み取り専用の2つだけ**です。動画の投稿・変更・削除はできません。
  - `youtube.readonly` … 動画の一覧・題名・説明文・タグ
  - `yt-analytics.readonly` … 自分のチャンネルの成績
  - `yt-analytics-monetary.readonly` … 収益（「収益」タブを開いて押したときだけ求めます）
- アクセストークンは、**この端末の保存領域に、期限（約1時間）付きで置きます**。
  開くたびにログインを求められるのを避けるためで、期限が切れれば自動で捨てます。
  外に送ることはありません（通信相手は Google だけです）。
  置きたくない場合は「設定」→「ログインしたままにする」を切ってください。
  切ると、開くたびに接続からやり直す代わりに、端末には何も残りません。
- 端末に残るのは、クライアントIDと、期限付きのアクセストークンと、
  30分で切れる取得済みデータの控えだけです。
  「設定」→「接続を解除する」でトークンだけ、
  「すべて初期化する」でまとめて消せます。

## 画面の作り（スマホを前提にしています）

この分析は、撮影の合間や移動中にスマホで開くものだと考えて作っています。
そのため次の順で組んでいます。

| 段 | 中身 | 理由 |
|---|---|---|
| 1段目 | 名前と、たまにしか押さないもの（更新・明るさ・設定） | 常時見えている必要はない |
| 2段目 | 見る場所（6つのタブ） | 設定はタブから外し、歯車に移した。設定は中身の画面ではないため |
| 3段目 | **見る期間（7日／28日／90日／1年）を横いっぱいに4つ** | いちばんよく押すため |

**期間はどのタブでも共通で効きます。** 収益を見ているときに「1年」を押せば、
収益が1年ぶんに入れ替わります。画面が概要へ戻ることはありません。

以前は期間を右上の隅に小さく置いていましたが、画面が狭いとチャンネル名に
押されて端で切れ、指で押せなくなっていました。**よく使うものほど広い面積を与える**
という原則を外していたのが原因です。選択肢は4つしかないので、
開いて選ばせるより並べたほうが1タップ速く済みます。

そのほかスマホ向けに決めていること：

- **押すところは最低44px。** これより小さいと押し損ねます（実測で毎回確かめています）
- **表を横スクロールさせない。** 動画一覧は狭い画面では1本を1枚の札にして縦に積みます。
  6列を横に送りながら読むと、どの数字がどの動画のものか分からなくなるためです
- **診断の表は28日と90日を必ず両方画面に入れる。** 片方が横スクロールの向こうに
  隠れると、見比べるというこの表の目的が果たせません
- **iPhone の下端（ホームバー）のぶんを空ける**
- **一番上の判定は、畳んだ状態で始まります。** 見えているのは
  「いまどうなっているか」の一言だけ。右の三角を押すと、そう判断した理由と
  28日／90日の表が出ます
- 「次にやること」も**畳んだ状態で始まります**。まず状態を読み、
  そのうえで「で、何をするのか」と思ったときに開く順番にしています
- どちらも、開いたか閉じたかはその端末に覚えます
